# 0.6 API, MCP, and agent skills execution plan

## Status and outcome

Status: planned after the 0.5 exit gate.

The phase outcome is one application service exposed consistently through the CLI,
a loopback preview API, MCP standard input, MCP Streamable HTTP, and thin agent skill
packages. The same input and authority must produce equivalent decisions, reason
codes, digests, and rewrite records through every surface.

The integrations do not contain rewrite, profile, or validation logic. Version 1.0
supports loopback HTTP only. Broader network exposure, TLS termination, remote
credentials, and a hosted service require a later threat model and authorization
design.

## Entry criteria

- Calibrated application outcomes and resource budgets pass the 0.5 gate.
- Stored profile schemas and application ports are stable enough for external use.
- Shared conformance fixtures can run without real model nondeterminism.
- The current MCP specification, SDK, conformance suite, and required client versions
  have been revalidated.
- Authority, local authentication, configuration, and content-redaction policies are
  approved.

## Required decisions

Accept decision records for:

- Wire DTO ownership and schema generation
- CLI configuration and machine-contract freeze policy
- Local API authentication and token storage
- API domain outcomes, RFC 9457 transport errors, and mutation concurrency
- `/v1` document-byte transfer, principal-scoped operation lifecycle, polling,
  cancellation, and progress metadata contract
- Exact MCP revisions, SDK version, transports, and client compatibility matrix
- Custom loopback bearer authorization profile for MCP HTTP, including its explicit
  exclusion from standard MCP OAuth authorization conformance
- MCP tool authority and learning-handle lifecycle
- Agent Skills packaging and installation trust
- Exact compatibility-adapter target, supported paths, provenance behavior, and
  ordinary-text proof, byte-splicing rules, and rewrite-record side channel

The experimental Skills over MCP proposal is not a 1.0 dependency. First-party
skills use the stable `SKILL.md` package format and call stable MCP tools or the
first-party API.

## Shared integration contract

Keep domain, persistence, and wire types separate. Every application request carries
an explicit context containing:

- Request and operation ID
- Authenticated local principal
- Authority scopes
- Deadline and cancellation token
- Resource budget
- Network policy
- Interface and schema identity
- Trace and raw-content policy

The canonical domain envelope distinguishes:

- Rewritten
- Unchanged
- Abstained
- Unsupported
- Cancelled
- Failed

The first-party HTTP mapping is normative for `/v0`:

| Application result | HTTP mapping while connected | Stable code | Retry | Body after disconnect |
| --- | --- | --- | --- | --- |
| Rewritten | 200 domain envelope | `rewrite.rewritten` | No | No |
| Unchanged | 200 domain envelope | `rewrite.unchanged` | No | No |
| Abstained | 200 domain envelope | `rewrite.abstained` | Only after explicit input or policy change | No |
| Unsupported | 200 domain envelope | `rewrite.unsupported` | Only after capability change | No |
| Cancelled | 200 domain envelope when cancellation is observed on a live request or later operation lookup | `operation.cancelled` | Caller choice | No |
| Failed | Typed 4xx or 5xx RFC 9457 problem, never a success envelope | Typed `input.*`, `auth.*`, `resource.*`, `compatibility.*`, or `operation.*` code | Only typed transient failures | No |

The API contract defines the exact status and problem type for every typed failure.
A disconnected response writes no later body or event even if backend cleanup
continues.

Abstention is a successful protected domain outcome. Transport, parsing,
authorization, resource, and operational failures use the error mapping appropriate
to each interface.

JSON Schema 2020-12 documents are generated from one reviewed source of truth,
checked in, diffed in continuous integration, and validated against positive and
malformed fixtures. External objects deny unknown properties unless the
compatibility policy explicitly allows them.

## Ordered work packages

### 1. Build the cross-interface conformance runner

- Feed equivalent owned requests to the application service through in-process,
  CLI, HTTP, MCP, and skill adapters.
- Compare status, stable reasons, gate summaries, source and output digests, profile
  version, model provenance, and redacted rewrite record.
- Normalize only documented interface metadata such as request IDs.
- Cover success, unchanged, abstention, unsupported, cancellation, deadline,
  authorization, malformed input, bounds, and operational failure.
- Run without network access or a real model through deterministic fakes.

No integration implementation is considered complete until its adapter passes the
shared fixtures.

### 2. Freeze the complete CLI contract

Define configuration precedence as:

1. Safe built-in defaults
2. User configuration
3. Explicit configuration file
4. Environment
5. Command-line arguments
6. Non-overridable security ceiling

Project configuration requires explicit trust. It cannot enable network access,
credentials, executable hooks, profile mutation, raw logging, or broader authority.
Restrictive policy is deny-wins, so a lower layer cannot override `--no-network` or
an equivalent security ceiling.

Detect standard input, output, and error terminal state independently. Keep JSON,
raw content, and rewritten data free of progress and styling. Interactive output
neutralizes terminal controls, bidi effects, hostile file names, and unsafe diff
content. Raw terminal output is removed or requires a specific double opt-in.

Process tests cover PowerShell, Bash, Zsh, and Fish completion generation, Unix
manual pages, pipes, terminals, `NO_COLOR`, broken pipes, Unicode, hostile controls,
symlinks, cancellation, and every exit category on supported platforms.

### 3. Implement the explicit local service lifecycle

- Start HTTP only through an explicit `serve` command.
- Keep ordinary desktop calls in process.
- Bind to an actual loopback address and report the final bound URL.
- Reject non-loopback configuration before socket creation.
- Generate or load a high-entropy local authentication token through an approved
  storage path.
- Separate rewrite, profile-read, profile-write, learning, and administration scopes.
- Set concurrency, queue, body, nesting, token, candidate, response, and time limits
  before accepting work.
- Shut down cleanly, cancel in-flight operations, and leave no partial mutation.

All application routes, including health and capabilities, require authentication.
Unauthenticated handling reveals no installed model, profile, path, build version,
scope, or configuration data. Tokens use operating-system protected storage with
restrictive file permissions where applicable, never appear in URLs or process
arguments, and are redacted from logs and crash reports. Rotation, revocation, and
deletion invalidate existing access predictably.

Localhost remains an authority boundary. Another local process or web page is not
trusted merely because it can reach a loopback port.

### 4. Implement the preview `/v0` API

- Publish capability, health, rewrite, check, profile, and explicit learning
  resources only as they gain conformance fixtures.
- Require authentication for every resource, including health and capabilities.
- Accept an absent Origin for authenticated non-browser clients and exact configured
  local origins. Reject `Origin: null`, malformed origins, and disallowed origins.
- Accept only valid bound Host values, reject mismatched Host, disable permissive
  CORS, and return no secret-bearing preflight response.
- Use explicit schema versions, stable string codes, request IDs, and redacted
  problem details.
- Use `application/problem+json` for transport, authorization, malformed request,
  resource, and operational errors.
- Return fidelity outcomes in the successful domain envelope, not as HTTP errors.
- Use conditional writes and client operation IDs for mutation idempotency rather
  than relying on an expired draft standard.
- Set every authenticated success and error response to `Cache-Control: no-store`.
- Cancel work on client disconnect or deadline.
- Return synchronous work only after complete validation and reassembly.
- Represent longer work with opaque principal-scoped operation resources,
  authenticated polling, and explicit cancellation.
- Stream or poll bounded phase, sequence, and progress metadata only. Never stream
  source content, candidates, output fragments, prompts, or trace content.
- Reject arbitrary client-supplied local paths. Inline JSON strings use logical text
  semantics; structured documents use the separately approved bounded byte or staged
  document contract.

OpenAPI and JSON Schema artifacts are checked in and compatibility-diffed. Unknown
routes, methods, media types, fields, versions, and oversized bodies fail before
application work begins.

Mutation replay state is namespaced by authenticated principal and operation ID. For
the same principal, an identical canonical request returns the retained result and a
different request with the same ID is a conflict. Another principal has a separate
namespace and cannot reveal or conflict with the first principal's record. Concurrent
duplicates share one committed operation. Retention is bounded and documented.
`If-Match` is part of the canonical request: its precondition is evaluated for the
first execution and the retained result is replayed even if later state changes.

### 5. Implement MCP over standard input

Target the exact approved MCP 2026-07-28 profile with pinned official Rust SDK
support. Modern MCP has no initialize exchange or protocol session. Requests carry
required protocol version and client capabilities plus optional `clientInfo` in
request metadata, and the server exposes `server/discover` as specified.

- Reserve standard output exclusively for newline-delimited JSON-RPC frames.
- Send diagnostics to standard error through the redacted logging policy.
- Bound frame bytes, nesting, inbound queue, concurrent calls, response bytes, and
  execution time.
- Use one serialized writer and cancellation-aware handlers.
- Declare structured input and output schemas with explicit bounds.
- Accept omitted optional `clientInfo`. Missing required protocol version or client
  capabilities returns JSON-RPC `-32602`; Streamable HTTP maps it to HTTP 400.
- Enable rewrite and check by default.
- Accept complete bounded TXT and supported Markdown content only in the baseline
  tools. Reject arbitrary paths, clipboard authority, raw audio, DOCX base64, and
  partial candidate streaming.
- Gate profile read, profile mutation, learning, and administration behind separate
  launch scopes.
- Return abstention as a successful structured tool outcome.
- Return one validated `structuredContent` result matching the checked output schema,
  with schema version, status, stable reason, complete output where applicable,
  source and output digests, and rewrite-record reference.
- Use protocol errors for malformed routing and tool execution errors for actionable
  runtime failure.
- Avoid new dependencies on deprecated roots, sampling, logging, and legacy HTTP and
  SSE behavior.

MCP may submit only a user-confirmed transcript to the typed interview contract.
Microphone, playback, device, and raw-audio authority remain exclusive to the local
CLI and desktop voice interfaces.

Support an older revision only for a named client and a complete compatibility
fixture. Do not promise every previous MCP version.

### 6. Implement explicit learning handles

- Generate opaque, high-entropy handles.
- Bind each handle to principal, authority, profile, purpose, protocol version, and
  expiration.
- Make handles revocable, single-purpose, and bounded by turn and data limits.
- Persist only the minimum state needed to reconstruct the workflow.
- Require explicit confirmation before any response becomes profile evidence.
- Expire and clean up on completion, cancellation, timeout, or authorization change.
- Never treat possession of a handle as authentication.

Protocol sessions are not application state. Each MCP request reconstructs
authorized learning state from the explicit handle.

### 7. Implement MCP over Streamable HTTP

Add the transport only after stdio behavior passes conformance.

- Implement modern POST-only Streamable HTTP.
- Require the client `Accept` header to list both `application/json` and
  `text/event-stream` and accept only a single-message POST body.
- Require and validate `MCP-Protocol-Version`, `Mcp-Method`, and applicable
  `Mcp-Name` headers.
- Reject header and body disagreement with the specified error.
- Support complete JSON and request-scoped SSE responses.
- Treat response-stream closure as cancellation.
- Validate Origin on every request and return 403 for invalid origins.
- Permit an absent Origin for non-browser clients, but reject a present invalid
  Origin with 403.
- Use the documented custom loopback bearer profile and bind only to loopback. This
  profile is not standard MCP OAuth authorization and is excluded from that portion
  of official conformance. Every named HTTP client must prove it can inject the token.
- Return 401 with a bearer challenge for a missing or invalid token and 403 for
  insufficient scope. Define rotation and revocation behavior.
- Do not emit a session ID, require sticky sessions, or add the removed modern GET
  endpoint. Ignore received `Mcp-Session-Id` and `Last-Event-ID` as specified for the
  modern transport.
- Keep profile-dependent discovery and list results private or uncached.
- Bound SSE queues and cancel slow or disconnected consumers.
- After stream cancellation, suppress every later message from the cancelled request.

Normative transport fixtures cover exact `HeaderMismatch` HTTP 400 and JSON-RPC
`-32020`, unsupported-version HTTP 400 and `-32022`, unknown-method HTTP 404 and
`-32601`, and GET and DELETE returning 405.

Tests cover malicious origins, unsupported versions, header mismatch, slow readers,
disconnects, cache headers, authentication, and accidental external binding.

### 8. Run official and product conformance

- Run all applicable official MCP conformance cases.
- Run the MCP Inspector against each transport.
- Validate every wire fixture against the checked-in schema.
- Pin exact SDK patch versions and record their license and advisory state.
- Add malformed frame, duplicate ID, invalid cancellation, unknown tool, oversized
  payload, queue saturation, and shutdown fixtures.
- Run required named client versions from clean installations.

Any protocol revision upgrade receives a compatibility diff, threat-model review,
and full conformance run before activation.

### 9. Package first-party Agent Skills

- Create separate routine rewrite and privileged profile-management skills.
- Use only stable `SKILL.md` frontmatter plus instructions, schemas, examples,
  compatibility ranges, offline behavior, explanatory authority requirements, and
  recovery guidance. Namespaced metadata may describe product requirements.
- Keep skills thin and call MCP or `/v0`.
- Include no validation, profile compilation, model logic, credentials, absolute
  local paths, or raw profile content.
- Avoid scripts unless a measured requirement justifies their execution and
  cross-platform burden.
- Validate packages with the reference validator and smoke-test explicit and
  model-selected activation.
- Require explicit local installation trust and never fetch skill content
  automatically during a rewrite.
- Enforce name and directory matching, field bounds, relative in-package references,
  and path and symlink containment.
- Never rely on experimental `allowed-tools` metadata for security. Real authority is
  enforced by the API or MCP server.

Any Skills over MCP experiment is separately labeled, isolated, and excluded from
the 1.0 release gate until the proposal becomes stable and qualified.

### 10. Build the compatibility adapter

The adapter is local shape-compatible post-processing, not broad upstream semantic
conformance.

- Pin the exact upstream schema revision and eligible JSON string paths.
- Accept only bounded, complete, non-streaming payloads.
- Require trusted request-side context proving ordinary final text semantics. If the
  adapter cannot rule out a structured-output request, return `Unsupported`.
- Classify duplicate keys as malformed and return no payload.
- Classify excessive nesting as a resource-limit error and return no payload.
- Classify well-formed tool calls, structured output, reasoning, refusals, citations,
  annotations, signatures, images, audio, and unsupported events as unsupported and
  return exact original bytes with `Unsupported` status.
- Use byte-range JSON string splicing so non-target payload bytes remain identical.
- Reparse and validate the complete output against the pinned schema.
- Apply document atomicity across all eligible text items.
- Return the original payload byte-for-byte on unsupported content, abstention, or
  verification failure.
- Make no network request and accept no upstream credential.
- Preserve upstream IDs, usage, and fingerprints while documenting that they refer
  to the original response.
- Emit the local rewrite record through the approved sidecar or envelope channel.

The machine-readable status side channel is decided before implementation. A
same-shape payload alone cannot safely communicate local abstention or provenance.

Adapter outcomes are exact:

| Input or decision | Payload result | Machine status |
| --- | --- | --- |
| Malformed | No payload | Typed invalid-input error |
| Oversized | No payload | Typed resource-limit error |
| Unsupported valid form | Exact original bytes | Unsupported |
| Rewrite abstention | Exact original bytes | Abstained |
| Final verification failure | Exact original bytes | Abstained with stable compatibility verification code |
| Verified rewrite | Validated spliced payload | Rewritten |

The rewrite record includes original and rewritten digests, pinned target schema,
eligible paths, adapter and validator versions, rewrite status, and a label stating
that retained upstream IDs, usage, and fingerprints describe the original response.

### 11. Freeze and publish preview contracts

- Compatibility-diff CLI JSON, API schemas, MCP schemas, skill metadata, and adapter
  fixtures on every change.
- Publish supported schema and protocol ranges plus deprecation policy.
- Include complete local examples that work with network access blocked.
- Document every authority, token, handle, limit, cancellation, and redaction rule.
- Retain contract reports as release artifacts.

The surface remains `/v0` until the 0.9 freeze. Preview changes require migration or
release notes once real clients or stored data depend on them.

## Security acceptance

- No HTTP service binds beyond loopback in 1.0.
- Every sensitive HTTP request requires authentication and valid Origin behavior.
- Profile mutation and administration are never bundled into routine rewrite
  authority.
- Standard output remains protocol-clean under MCP stdio.
- Slow clients, queues, retries, bodies, and event streams are bounded.
- Cancellation never emits a partial rewrite or commits partial mutation.
- Logs, errors, schemas, skill packages, and traces contain no content or credential
  by default.
- Skills and compatibility payloads are untrusted input.
- The compatibility adapter contains no outbound network or credential code path.

## Required test matrix

| Surface | Required evidence |
| --- | --- |
| Shared service | Equivalent outcomes, authority, budgets, cancellation, and redaction |
| CLI | Configuration precedence, terminal safety, streams, paths, exits, completion, and manuals |
| API | OpenAPI, JSON Schema, all-route auth, token lifecycle, absent, allowed, null, malformed, and disallowed Origin, preflight, bound and mismatched Host, no-store success and errors, principal-scoped operation replay, `If-Match`, overload, and disconnect |
| MCP stdio | Official conformance, Inspector, required and optional metadata, frame bounds, stdout purity, cancellation, scopes, and shutdown |
| MCP HTTP | Accept and metadata headers, exact errors, versions, methods, JSON, SSE, absent and invalid Origin, custom bearer auth, ignored legacy headers, cancellation suppression, cache, slow readers, disconnect, and loopback |
| Skills | Stable frontmatter, name and directory, field bounds, package containment, reference validation, explicit activation, model-selected activation, authority separation, and offline use |
| Adapter | Exact outcome mapping, pinned schemas, byte identity, unsupported events, atomicity, provenance labeling, malformed JSON, and fuzzing |

Overall Rust line coverage remains at least 80 percent. Authorization, protocol
translation, terminal safety, schema validation, learning handles, and JSON splicing
target at least 90 percent and receive mutation or equivalent adversarial testing.

## Exit evidence

The phase closes only when:

- Shared fixtures produce equivalent application decisions through every interface.
- Applicable official MCP conformance cases and required client smoke tests pass.
- No service binds beyond loopback and no authority is silently broadened.
- Skills contain no duplicated product logic and use stable package semantics.
- The protocol-level skills experiment remains non-blocking and clearly
  experimental.
- Unsupported compatibility payloads return unchanged with documented status.
- Cross-platform clean-install, offline, cancellation, and removal tests pass.
- All four refinement passes are complete with no open critical authorization,
  protocol, privacy, or compatibility defect.

The handoff to 0.7 includes stable application interfaces, complete authority and
resource contexts, conformance fixtures, and an adapter-independent document API
that can expose DOCX capabilities without weakening their preservation contract.
