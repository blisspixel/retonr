# Milestone 0.2 runtime admission work package

## Status and objective

This is the active trust-boundary work package inside milestone 0.2. Its objective is
to admit one exact CPU-only Linux x86-64 GNU libc runtime package from retained
source-build evidence, then prove one managed read-only startup under the existing
local-only isolation boundary.

The outcome is deliberately narrow: the package becomes eligible for the managed
read-only review path. It is not model qualification, generation admission,
activation, user-facing `retonr` CLI exposure, or a support claim. The existing
generation bracket additionally requires a separate exact package-and-worker review.

## Why this is next

The current production cloud-disable and generation-path allowlists are both empty.
Managed review, effective-state work, model-package lease join, candidate receipt,
locked evaluation, and real CLI composition all depend on one admitted runtime root,
but runtime admission alone must not authorize generation.

The official Ollama v0.32.15 archive cannot pass the existing source-lineage control
because its tagged build disabled provenance and SBOM output and did not freeze its
complete builder inputs. More execution tests cannot establish that missing
relationship. [ADR 0010](../decisions/0010-controlled-runtime-source-build.md)
therefore selects a controlled source build without changing the historical blocked
review.

## Preconditions

- Preserve the schema-9 store, including all unchanged schema-6 lifecycle and package
  tables, leases, isolation, attestation, retained-connection, cancellation, and
  cleanup behavior.
- Preserve the official archive review as non-admitted evidence.
- Add no model or runtime download to an ordinary product command.
- Keep production generation blocked until a canonical all-pass runtime admission
  record and a separate exact package-and-worker generation review are both present
  and checked by their independent policies.
- Run the controlled build only from a separately authorized manual workflow or a
  local operator command with caller-supplied frozen inputs.
- Claim managed generation only on Linux x86-64. Windows and macOS remain
  deterministically unsupported for this package.

## Ordered implementation

### 1. Retain the controlled-build review contract

Use the implemented additive `RuntimePackageReviewV2` contract. Keep schema v1
readable and unchanged.

Implementation status on 2026-08-26: the offline schema-2 verification foundation is
implemented in `rewrite-ollama-package`. It keeps schema 1 unchanged, enforces
canonical bounded review JSON, hashes every referenced metadata stream, validates a
typed canonical frozen input manifest and every component byte in its derived
artifact set, reconstructs candidate member bytes, and independently derives the final
runtime-package identity. Its compiler accepts only portable evidence paths, classes,
and ordered control results, reconstructs blocked candidates to derive their identity
fields without exposing a runtime lease, derives blockers from incomplete controls,
and matches the canonical all-pass fixture byte for byte. The input contract
requires explicit source, module, checksum, toolchain, compiler, assembler, linker,
build-script, native-package,
standard-library, helper, and license roles plus an offline CPU-only policy. Its
dedicated local suite clears the critical-path 90 percent line-coverage target. No
production review record or policy consumes it yet.

The v2 parser must:

- reject unknown, duplicate, missing, noncanonical, or reordered fields and controls;
- bind one canonical source-build input manifest and every referenced evidence file;
- verify evidence bytes against their declared digest instead of trusting copied
  digest text;
- distinguish fetched inputs, build tools, build output, execution evidence, and
  admission disposition;
- require every control exactly once;
- allow no final layout or package identity on an incomplete disposition;
- reconstruct the final layout and independently derive the all-pass
  `RuntimePackageManifestId`.

Keep review JSON at or below the existing 256 KiB ceiling unless a reviewed schema
change proves a larger bound necessary. Keep referenced metadata at no more than 128
records, 4 MiB per record, and 64 MiB aggregate. Large source and toolchain objects
remain content-addressed artifact-set members, not inline JSON.

### 2. Compile one deterministic admission bundle

Use the implemented offline bundle validator and compiler, which consume only
caller-selected local paths. They produce canonical content-free review output and
never mutate the source bundle.

The bundle must inventory:

- exact Ollama and llama.cpp source revisions and archive digests;
- Go toolchain and module content;
- OCI image digests and exact native package payloads;
- compiler, assembler, linker, CMake, Ninja, retained POSIX shell,
  standard-library, and build-script identities;
- environment, target, CPU feature, build argument, locale, timezone, and source
  epoch policy;
- isolation-helper bytes and build evidence;
- license, SBOM, provenance, transformation, and rebuild comparison evidence.

Use the current runtime layout ceilings: 64 KiB JSON, at most 64 package members,
and at most 4 GiB for any one member. Every aggregate byte count must use checked
arithmetic and an explicit caller ceiling.

Implementation status on 2026-08-25: the read-only application bundle boundary is
implemented. It validates caller ceilings before source access; pins a separately
selected manifest and component root; requires the exact declared files and implied
directories; rejects indirect, multiply linked, missing, extra, changed, oversized,
or digest-drifting input; retains the verified file handles; and exposes no local
path in its result. The input contract now carries the explicit sorted environment
and ordered build arguments instead of accepting uncheckable copied digests. It
requires the offline Go baseline (`GOPROXY=off` and `GOSUMDB=off`) and derives a
content-free build-plan digest from the complete frozen handoff.

The input contract has a 4 MiB manifest ceiling, 1,024 component ceiling, 64 GiB
per-component ceiling, and 512 GiB aggregate ceiling. A caller may only lower those
bounds. The exact tree boundary additionally limits files plus directories to
262,144 by default and lets callers lower that ceiling.

A typed two-attempt build-report compiler and verifier are also implemented. They
hash the exact layout, SBOM, provenance, transformation, portable output-tree,
isolation, standard-output, and standard-error evidence for each attempt, reconstruct
both runtime member trees, check their source-set, target, environment, argument, and
build-plan bindings, and derive whether the outputs are byte-identical or different.
The app-owned output-tree sidecar binds every original path, entry kind, ordinary Unix
permission bits, file size, and file digest to the retained helper commitment.
Set-user-ID, set-group-ID, and sticky bits are rejected before output commitment or
export. An accepted permission-only difference therefore produces a nonidentical
comparison. The compiler derives the canonical
schema-2 report from opened bytes instead of accepting copied output identities.

A static offline source-builder coordinator and two developer-only preparation
binaries are implemented in `rewrite-runtime-source-builder`. The coordinator is the
reviewed build target inside capability ABI 2. It independently revalidates its input
and private-output descriptors against their fixed aliases, requires the private
output as its working directory, extracts the exact frozen archives, applies the
retained transformations, invokes the frozen toolchain, assembles the runtime tree,
and writes layout, SBOM, provenance, and transformation evidence. The preparation
binaries normalize already-fetched local trees and compile the frozen manifest and
evidence. They perform no fetch and grant no admission, qualification, activation,
generation, or user-facing `retonr` authority.

The application now runs two fresh Linux attempts from a retained helper and build
program, an exact path-to-retained-file map, and a retained host-output object. Each
attempt uses fresh user, PID, network, and private mount namespaces. The mount tree is
made recursively private and a fresh 16 GiB, 262,144-inode tmpfs is mounted at `/tmp`.
The byte quota reserves 4 GiB of bounded build scratch beyond the 4 GiB private-input
and 8 GiB committed-output ceilings.
Before the first probe, the parent copies the exact expected helper bytes into an
executable anonymous file, verifies its declared size, SHA-256, and trailing EOF,
applies immutable size and write seals, and retains only that sealed helper snapshot.
Stage one constructs `/tmp/retonr-controlled-build/input` from normalized private
directories and copies every exact retained-file declaration from offset zero. It
verifies declared size, SHA-256, trailing EOF, single-link regular-file type, and
before-and-after retained identity, normalizes modes to read-only or read-execute, and
remounts the complete input root read-only. The aggregate declaration is rejected
above 4 GiB before any private member is created. The caller's input root is not
passed to the helper or target. The
fixed `/tmp/retonr-controlled-build/output` alias is a distinct initially empty
directory in the private tmpfs. The retained host output is neither mounted nor
passed to the target. Controlled-build capability ABI 2 supplies the private-input and
private-output aliases and inherited descriptors to the target. The parent
independently observes and retains the mount namespace before execution. The helper
revalidates the program, mapped input files, private aliases, and host-output object.
The builder independently revalidates the capability ABI, input and private-output
descriptor-to-alias identities, and output working directory. Landlock ABI 3 grants
input read and execute access, exact read and write access to `/dev/null`, and write
access only to the private output while denying other device files.

This closes caller-root pathname substitution, same-inode mutate-and-restore races,
and target-side input writes for the bytes consumed by the target. The target receives
only the digest-verified private copy after the input root is read-only. The
application still revalidates retained evidence before accepting the result. These
checks establish exact byte and boundary behavior only; they do not decide source
lineage, license, transformation correctness, reproducibility, or semantics.

The environment is cleared and rebuilt from the verified plan. Time, cancellation,
and process-tree teardown are bounded. Child-tool streams are drained concurrently;
successful output is discarded and a failing stage may relay only its final 16 KiB per
stream. The outer boundary retains at most a 32 KiB prefix per stream. Stage two does
not report completion until the coordinator is reaped and descendant-held diagnostic
streams close; the guardian waits for stage two to exit before it inspects output.

The guardian accepts only directories and single-link regular files in the private
output, commits at most 4,096 entries and 8 GiB of regular-file bytes, and binds paths,
modes, sizes, and content digests. It recomputes that commitment before export, copies
from retained private-file handles into the distinct initially empty host output
without replacement, rehashes source bytes during copy, and requires an exact
recommitment of the host tree. Export is not atomic; any failure leaves the partial
host tree inert and fails the attempt. The application then independently enumerates
and rehashes the host tree, requires exact equality with the helper commitment, and
retains member handles, fingerprints, and byte digests. This application seal detects
substitution and later drift but is not an operating-system write lock.

Nonzero status, truncated outer streams, source and output overlap, overlapping attempt
roots, input drift, aliasing, helper commitment mismatch, export substitution, and
unexpected or changing output-tree entries fail closed. App-owned isolation and stream
evidence remain distinct from build-owned output files. The app-owned portable
output-tree sidecar is also distinct from the original output and retains its exact
ordinary Unix permission bits even when durable container permissions are normalized.
Special permission bits fail closed rather than being normalized. Raw streams remain
out of serialization and debug output.

A static Linux native regression executes that complete fixture path twice, derives
one byte-identical report, publishes its complete source, output, managed-evidence,
and report closure through an application-owned staging tree, and independently
reacquires and rehashes the published bytes. Publication first uses a bounded
empty-tree probe to verify exact no-replace rename support for the selected parent before report
compilation or retained-byte copying. It then derives a canonical artifact-set
manifest, validates file and directory counts and aggregate bytes before creating the
populated staging tree, rejects overlapping boundaries and existing destinations,
synchronizes the verified tree bottom-up, and uses a no-replace rename. Reacquisition
requires an exact single-link tree and independently verifies the frozen inputs, build plan, report,
both runtime packages, and comparison. The native regression also proves later
evidence drift fails closed. It then compiles a schema-2 review directly from the
retained durable root, independently verifies the canonical bytes against the same
closure, and proves the result remains blocked with source lineage, transformation,
license, native closure, managed startup, and cloud disable all unrun. This establishes
the implemented retained build, durable evidence, and blocked-review mechanisms on
the tested kernel and filesystem. A direct import bridge accepts only a byte-identical
two-attempt closure, copies and rehashes only the primary report's declared runtime
members, revalidates immediately before no-replace publication and after durable
package readback, and leaves both production policy allowlists unchanged.
It is not a formal confinement guarantee and does not admit a runtime. On 2026-08-26,
the real frozen Ollama v0.32.15 closure completed two byte-identical controlled builds.

### 3. Split fetch from the offline build

The separate runtime-admission evidence root now has a read-only exact-tree
verifier and retained byte lease. It requires twelve fixed evidence members, four
directories, and a canonical manifest, parses the canonical foundation, enforces
member and aggregate bounds, and freshly rehashes the complete closure before
member access. The remaining member bytes are opaque. This mechanism does not
publish an admission bundle, verify the six semantic controls, or grant admission.
The initial inert assembly compiler and publisher now derive a complete bounded
byte root from a source-build-bound foundation and eleven opaque member snapshots.
They verify staging, synchronize, publish without replacement, and independently
reacquire the exact closure. This does not validate the opaque members' semantic
relationships or derive passed controls or production policy. The
[durable evaluation and folder checks batch](0.2-durable-evaluation-and-folder-checks.md)
records this boundary.
The successor [runtime observations batch](0.2-judge-settlement-and-runtime-observations.md)
exercises that public adapter through an actual retained synthetic source-build
lease in the forced networkless native fixture. It also adds a consuming managed
observation route that completes cleanup and package revalidation before returning
canonical records, preserving `Unreviewed` cloud status. This route does not mint
Passed controls or weaken the independent reviewed-only verification gate. A real
runtime build, observation, and semantic review remain required.
The next semantic composition must derive those exact members from verified authorities
and independently verify their subject relationships.

The fetch phase resolves every permitted immutable source into a content-addressed
input bundle and records license and source evidence. It has explicit network
authority and no admission authority.

The build phase runs with outbound network access denied. It reads only the verified
bundle, emits a CPU-only candidate, an SBOM, provenance, build logs, exact member
digests, and a rebuild comparison. It must fail on an undeclared read, dependency
fetch, accelerator output, unexpected package member, or nondeterministic input.

Run two isolated builds where the selected toolchain supports it. Record exact byte
equality or disposition every difference before admission. Do not label an
unverified build reproducible.

### 4. Discover and freeze external components

Use the implemented explicitly non-authoritative discovery surface for executable
external mappings. Discovery output proposes a sorted set of artifact digest, byte
size, and mapping class records. It cannot enter an admission record directly.

Review that set, then run the existing native-load observer again with the frozen
set as input. The verification run fails on any new, absent, changed, deleted,
anonymous executable, or preloaded component.

Implementation status on 2026-08-25: the observer now has a separate Linux discovery
operation that brackets two complete object-bound mapping snapshots and emits a
canonical content-free report with `authority: none` and `status: proposed`. Its
result type is distinct from the verifier's expected-component type. A frozen-set
compiler and independent verifier bind the exact canonical discovery report, runtime
package, component sequence, and a separate bounded reviewer-owned evidence record.
Only the verified frozen set exposes the expected-component slice consumed by the
existing second observation. Windows and macOS return deterministic unsupported
results. The real candidate still needs its discovery run, review record, and frozen
verification run.

Reuse the native observer's hard ceilings: at most 65,536 mapping regions, 16 MiB of
mapping metadata, 4,096 loaded components, 8 GiB of aggregate hashing, and 120
seconds. The qualification plan should select much smaller caller bounds from the
observed CPU candidate.

### 5. Run managed startup and cloud-disable controls

Use the implemented non-authoritative two-operation review runner. Its discovery
operation constructs the managed isolation lease from the exact retained package,
launches only the retained entrypoint, reparses canonical native discovery output,
and always performs cleanup with a fresh cancellation token. Its final operation
consumes the separately verified frozen native set, repeats exact launch and process
binding, performs the retained version probe, records native-load and managed-final
facts, independently re-derives both records, and returns opaque foundation-bound
native-closure, managed-startup, and cloud-disable passed controls. Primary and
cleanup errors remain distinct, and neither operation mutates policy or grants
admission.

The remaining orchestration work is to persist and independently reacquire the exact
native and managed records in the derived admission ledger, combine them with the
three static passed controls, and compile and independently verify one canonical
six-control all-pass schema-2 review. The real Linux candidate still needs both
operations and the retained evidence run; Windows and macOS remain fail-closed.

The in-memory authority join is implemented. It accepts only all six exact passed
controls plus an independently verified canonical all-pass schema-2 review, binds
the native record and frozen external-component set through both managed controls,
and returns a nonserializable admitted-runtime capability. A separate join requires
the production generation-path policy to review the exact package, version, source,
worker, native record, and frozen set before it returns a second nonserializable
capability. Both production allowlists remain empty, so these joins cannot authorize
the real candidate. Durable evidence production and policy review remain required.

Require:

- an exact retained runtime-package lease and helper;
- a cleared and explicit launch environment;
- exactly `OLLAMA_NO_CLOUD=1` and one nonconflicting cloud-disabled startup marker;
- loopback-only namespaces, capability reduction, no-new-privileges, and inherited
  seccomp;
- exact version, package, process, connection, native-load, and external-component
  identities;
- one retained read-only loopback request and clean process-tree teardown;
- at most 32 KiB per startup stream and existing HTTP body and elapsed-time bounds.

No completion traffic is allowed in this work package.

### 6. Derive admission policy from retained evidence

An all-pass bundle carries the exact layout digest and
`RuntimePackageManifestId`. Generate or validate the cloud-disable production policy
from that record. A separately typed version string or manually copied package
identifier cannot add authority. Runtime admission does not populate the independent
exact package-and-worker generation-path allowlist.

Retain the complete evidence bundle durably. A short-lived hosted workflow artifact
may verify a bundle, but it is not the sole evidence ledger.

### 7. Close the composed-path test gap

Add a non-shipping deterministic harness around the real managed orchestration.
Exercise every admission decision, operation and cleanup combination, cancellation
point, drift result, and unsupported platform result without changing the production
allowlist.

The composed managed preflight and generation authorization modules are critical
paths. Bring their line coverage above 90 percent and represent every security

## Failure, cancellation, and privacy

- Parsing, discovery, build, import, startup, observation, or cleanup failure leaves
  the candidate non-admitted.
- Cancellation is checked before every expensive read, hash, build stage, launch,
  request, and final publication boundary.
- Cleanup uses a fresh bounded cancellation context and reports combined operation
  and cleanup failures without hiding either class.
- Reports contain identities, counts, bounds, statuses, and digests only. Source,
  prompts, environment values other than approved policy names, local paths, process
  arguments, and raw startup logs stay out of serialized admission output. Raw
  child-tool diagnostics remain sensitive process output. Successful stages discard
  them; failed stages relay only bounded tails into the nonserializable outer capture.
- The build and qualification operation remains offline after the explicit fetch and
  artifact setup phase.

## Verification matrix

- Unit tests: schema, canonical ordering, identity derivation, limits, and error
  mapping.
- Golden fixtures: admitted, blocked, unrun, malformed, drifted, and superseded
  bundles.
- Property tests: ordering, duplicate rejection, digest sensitivity, and disposition
  completeness.
- Process tests: network-disabled build, environment clearing, marker conflicts,
  startup timeout, cancellation, teardown, and combined failures.
- Controlled-build ABI tests: capability ABI mismatch, fixed-alias substitution,
  descriptor, path, program, or working-directory identity mismatch, helper-reported
  mount-namespace mismatch, root replacement, private tmpfs byte and inode quotas,
  absence of target access to the retained host output, and nonempty output rejection.
- Controlled-output tests: descendant-held stream drain before commitment, final-tree
  entry and byte ceilings, unsupported entry rejection, helper commitment mismatch,
  verified host export, export-time substitution, independent application rehash, and
  post-seal drift detection.
- Diagnostic tests: saturate both child streams, prove concurrent draining without
  deadlock, retain only the final 16 KiB on failure, discard successful child output,
  and enforce the outer 32 KiB prefix bound.
- Native tests: expected and unexpected external components, preload, deleted
  mappings, worker presence, and unsupported platforms.
- Policy tests: no incomplete review can populate the cloud-disable allowlist, an
  admitted record cannot diverge from its layout or package identity, and runtime
  admission alone cannot populate the separate generation-path allowlist.
- Coverage: repository line coverage remains at least 80 percent; review,
  authorization, and composed managed paths remain above 90 percent.
- Repository gates: formatting, check, strict Clippy, tests, docs, audit, deny,
  repository policy, Markdown lint, Linux isolation, and networkless native success.

## Non-goals

- Model acquisition, qualification, activation, or generation
- GPU, accelerator, Windows, or macOS runtime support
- Attached-process admission or fallback
- User-facing CLI commands
- Effective runtime state, model-use proof, handler proof, or semantic authority
- Profiles, Markdown, DOCX, MCP, plugins, desktop, installers, or release claims

## Completion evidence

This work package closes only when one durable source-built bundle has all controls
passed; its layout and runtime-package identities reconstruct exactly; the production
policy is derived or validated from that record; managed read-only startup and
teardown pass on the controlled Linux qualification host; the composed critical
paths meet their coverage target; and current state records the exact revision,
workflow, evidence, limitations, and rollback.

The next work package then adds generation-bound provider, effective configuration,
platform, driver, compute-backend, and device-placement evidence inside the retained
generation bracket.
