# 0.7 bounded DOCX execution plan

## Status and outcome

Status: planned after the 0.6 exit gate.

The phase outcome is a secure adapter for a narrow, explicit WordprocessingML
subset. It preserves untouched package-part content, changes only approved text-node
ranges, validates the resulting package, and abstains when formatting or package
behavior is ambiguous.

This phase does not promise character-level formatting preservation for arbitrary
rewrites, lossless handling of every Word feature, binary-identical ZIP output, or
support for macro-enabled, encrypted, signed, or revision-heavy documents.

## Entry criteria

- Application, CLI, API, and adapter contracts pass their prior gates.
- The supported DOCX feature matrix and preservation definition are approved.
- ZIP, XML, relationship, and total-work limits are approved.
- Test licenses allow checked-in synthetic and compatibility fixtures.
- Office software and schema-validation procedures are available on the qualification
  systems.

## Required decisions

Accept decision records for:

- OPC package reader and writer strategy
- ZIP metadata, entry ordering, timestamp, compression, and reproducibility policy
- XML parser, namespace, entity, depth, and byte-splice policy
- Story, paragraph, table, run, whitespace, and hyperlink support matrix
- Homogeneous formatting eligibility and replacement distribution across text nodes
- Unsupported feature detection and atomicity behavior
- Package, XML, relationship, structural, and office-reopen verification
- Output naming, backup, source overwrite, and signed-document policy

## Initial support matrix

Supported eligibility is limited to:

- Unencrypted `.docx`
- Main document story only
- Ordinary paragraphs and table-cell paragraphs
- Contiguous text represented by approved `w:r` and `w:t` patterns
- Homogeneous effective run formatting across a rewrite unit
- No unsupported field, revision, content control, drawing, equation, object, or
  boundary inside the unit
- Protected hyperlink targets with separately qualified visible text behavior
- A package inside all declared resource limits

The first release rejects or protects, according to the capability matrix:

- `.docm` and macro parts
- Encrypted packages
- Package signatures
- Tracked insertions, deletions, moves, and ambiguous revision state
- Fields and field-code boundaries
- Content controls
- Drawings, text boxes, equations, embedded objects, and OLE
- Footnotes, endnotes, headers, footers, comments, glossary, and other stories as
  rewrite targets
- Mixed run formatting inside a proposed unit
- External relationship traversal
- Unsupported or malformed XML and package relationships

Unknown untouched parts may be preserved opaquely only when the package remains
within policy and no unsupported feature affects an eligible unit or invalidates the
document-level claim.

## Preservation contract

For an advertised supported input:

1. The original package is never modified in place during parsing or generation.
2. Every untouched package part has identical decompressed bytes in the output.
3. Within a touched XML part, only approved `w:t` text and required `xml:space`
   attribute ranges change.
4. Relationships, content types, namespaces, and protected targets remain valid and
   equivalent.
5. The structural fingerprint for supported WordprocessingML remains equivalent.
6. The output passes package and XML validation plus the declared office-reopen
   checks.
7. A final failure returns the original package under document-atomic policy.

ZIP container bytes, compression streams, entry timestamps, and ordering may differ
unless the separate reproducibility policy requires otherwise. Documentation must
distinguish package-part content preservation from binary archive identity.

## Ordered work packages

### 1. Build the capability matrix and fixture taxonomy

- Assign stable capability IDs for package, story, block, run, field, revision,
  relationship, and object features.
- Mark each as supported, protected, unsupported, or rejected.
- Create minimal synthetic positive, negative, malformed, adjacent, and interaction
  fixtures.
- Include documents produced by supported versions of Microsoft Word and at least
  one independent office implementation where practical.
- Record expected package parts, relationships, content types, eligible text nodes,
  and preservation hashes.

No feature changes status without its full parse, plan, apply, verify, security, and
office-compatibility evidence.

### 2. Implement a bounded OPC reader

- Read entries directly from the archive without extracting paths to disk.
- Validate normalized part names and reject traversal, absolute paths, duplicate
  normalized names, ambiguous case collisions, and illegal encodings.
- Bound archive bytes, entry count, per-entry compressed and expanded bytes, total
  expanded bytes, compression ratio, metadata bytes, and processing time.
- Reject unsupported encryption and multi-disk behavior.
- Record content hashes while streaming bounded entry data.
- Preserve unknown safe parts as opaque bytes.
- Treat ZIP metadata and every part as untrusted.

Resource-limit failure occurs before large allocation or XML parsing.

### 3. Validate package topology

- Parse `[Content_Types].xml`, root relationships, and document relationships with
  strict bounds.
- Resolve internal targets without filesystem semantics.
- Detect external relationships and never fetch, resolve, preview, or activate them.
- Locate the main document part through relationships rather than a fixed path.
- Detect macro, signature, encryption, embedded object, and unsupported content
  types before rewrite planning.
- Validate that required parts and relationship IDs are unique and coherent.

Topology is represented in adapter-owned state. Core rewrite code receives no ZIP or
relationship authority.

### 4. Parse XML securely and loss-consciously

- Disable DTD and external entity behavior.
- Bound XML bytes, depth, attributes, namespace declarations, text nodes, and events.
- Preserve original XML bytes and retain byte anchors for approved text content.
- Decode entities only for the semantic rewrite view and retain the original source
  representation for verification.
- Validate namespace identities rather than relying on prefixes.
- Reject malformed, ambiguous, duplicate, or unsupported constructs in an eligible
  region.
- Retain `xml:space` behavior and significant leading or trailing spaces explicitly.

The writer uses narrow byte splices for eligible text rather than reserializing an
entire XML part.

### 5. Discover stories and structural units

- Enumerate package stories and report their support state.
- Select only the main document story for initial rewriting.
- Parse paragraphs and table-cell paragraphs while preserving table grid and merge
  information in the structural fingerprint.
- Exclude content inside unsupported revisions, fields, controls, drawings, objects,
  bookmarks with ambiguous ranges, or other unsupported boundaries.
- Build rewrite units from contiguous approved text nodes with stable source anchors.
- Protect paragraph properties, run properties, tabs, breaks, symbols, and non-text
  children unless separately qualified.

Story discovery does not imply rewrite support. Unsupported stories remain
byte-identical.

### 6. Establish effective formatting eligibility

- Compare the exact supported run-property representation across a proposed unit.
- Require homogeneous effective formatting under the defined subset.
- Treat theme, style inheritance, direct formatting, language, proofing, hyperlinks,
  and revision boundaries conservatively.
- Reject a unit when the adapter cannot determine where rewritten words should
  inherit formatting.
- Record formatting fingerprint and source node sequence in adapter state.

Visual similarity from one office renderer is not sufficient evidence of formatting
equivalence.

### 7. Plan text-node replacement

- Map a rewrite unit to an ordered sequence of approved `w:t` byte ranges.
- Require the source digest, package topology version, XML fingerprint, and node
  sequence to match before applying an edit.
- Escape XML text safely without introducing elements or entities with new meaning.
- Apply a deterministic distribution policy across existing approved nodes.
- Change `xml:space` only when required to preserve leading or trailing whitespace,
  and include that change in the approved plan.
- Bound replacement bytes and output growth.
- Reject stale, overlapping, ambiguous, or cross-boundary edits.

The distribution policy is qualified with Word and independent office fixtures. It
never creates, removes, merges, or reorders runs in the initial subset.

### 8. Rebuild the package conservatively

- Copy untouched part bytes exactly.
- Apply approved byte splices only to touched XML parts.
- Preserve required ZIP metadata according to the accepted policy.
- Write to a new temporary file in the destination directory.
- Flush and complete the platform-tested replacement or new-file operation.
- Never overwrite the source by default.
- Reject symlink, case-collision, cross-device, lock, permission, and ambiguous target
  behavior.

Cancellation removes temporary output and does not alter the source.

### 9. Verify the complete output

- Reopen the output as a bounded OPC package.
- Recompute all untouched-part hashes.
- Verify touched-part non-target byte identity.
- Revalidate content types, relationships, internal targets, namespaces, XML, and
  structural fingerprints.
- Compare protected destinations, fields, objects, and story inventories.
- Reparse the resulting visible text and run the document-level fidelity checks.
- Validate using the selected OOXML package or schema tooling.
- Open and resave dedicated qualification copies in supported office software while
  retaining the original output for byte-level evidence.

An office application repairing the file is a failure, not successful compatibility.

### 10. Add security, properties, and fuzzing

Properties include:

- No-edit output preserves every package-part byte.
- An approved edit cannot change an untouched part or non-target XML range.
- All internal relationship resolution remains inside the package namespace.
- Parser and writer limits are monotonic and enforced before allocation.
- Failed or cancelled application produces no committed partial output.

Fuzz ZIP metadata, part names, content types, relationships, XML events, namespace
combinations, text-node mappings, replacement escaping, and package rebuild. Retain
and minimize every crash, hang, excess allocation, or false-preservation case.

### 11. Integrate through every interface

- Report detected DOCX capabilities and reasons through CLI, API, MCP, and desktop
  DTOs without exposing document content.
- Keep generation, profile, and validation behavior format-independent after units
  are created.
- Support check, dry-run, trace, output, and explicit atomicity before in-place use.
- Treat unsupported documents as a stable domain outcome.
- Keep compatibility-adapter behavior independent from DOCX package handling.

Shared conformance fixtures verify equivalent interface outcomes.

### 12. Qualify and document the subset

- Run synthetic, Word-produced, independent-office, malformed, adversarial, and
  resource fixtures on Windows, macOS, and Linux.
- Publish the exact feature and office-version matrix.
- Record package size and processing resource bounds.
- Document why unsupported features are protected or rejected and how to recover.
- Add real screenshots only when a supported document successfully completes the
  passing release workflow.

## Security acceptance

- No package path is extracted to the filesystem.
- DTD and external entity behavior is unavailable.
- External relationships are never followed.
- ZIP and XML resource limits apply before unbounded allocation.
- Macro-enabled, encrypted, signed, and ambiguous revision documents are handled
  exactly as declared.
- The source is never overwritten by default.
- Temporary output is cleaned up on failure or cancellation.
- Untrusted document text is never rendered as trusted HTML or logged by default.

## Required test matrix

| Area | Required evidence |
| --- | --- |
| OPC | Part names, duplicates, case collisions, content types, relationships, external targets, and bounds |
| ZIP | Bombs, ratios, counts, sizes, truncation, corruption, encryption, metadata, and cancellation |
| XML | DTD, entities, namespaces, depth, attributes, malformed events, escaping, and `xml:space` |
| WordprocessingML | Paragraphs, tables, runs, properties, links, revisions, fields, controls, drawings, and objects |
| Preservation | Untouched parts, non-target XML, structural fingerprints, protected targets, and stale anchors |
| Compatibility | Word and declared independent office versions on supported platforms |
| Filesystem | New output, overwrite opt-in, locks, permissions, symlinks, long paths, cleanup, and recovery |

Package parsing, XML anchoring, edit planning, apply, and verification target at
least 90 percent line coverage with every security-sensitive branch represented.
Overall Rust line coverage remains at least 80 percent.

## Exit evidence

The phase closes only when:

- Every advertised feature passes package, structure, fidelity, and office-reopen
  fixtures.
- Untouched part bytes and touched-part non-target bytes meet the preservation
  contract.
- Unsupported content never receives a false preservation claim.
- Malicious packages fail within resource limits and without side effects.
- Cross-platform output, lock, cancellation, and recovery tests pass.
- The support matrix and user-facing limitations match implementation exactly.
- All four refinement passes are complete with no open critical security, structure,
  compatibility, or data-loss defect.

The handoff to 0.8 includes a stable capability and verification API that the desktop
can present without implementing its own document rules.
