# 0.4 Markdown execution plan

## Status and outcome

Status: planned after the 0.3 exit gate.

The phase outcome is a source-splice Markdown adapter for a deliberately small,
declared dialect and syntax subset. It rewrites only eligible prose spans, preserves
all non-target bytes, reparses the output, and abstains when the adapter cannot
support its preservation claim.

This phase does not promise a lossless mutable Markdown syntax tree, arbitrary
extension support, raw HTML rewriting, or preservation for every construct accepted
by every renderer.

## Entry criteria

- Plain-text rewrite, validation, profile, and CLI behavior pass their prior gates.
- The adapter port can parse, plan, apply, verify, and report capabilities without
  depending on generation.
- The initial dialect and supported-feature matrix are approved.
- Security policy defines executable Markdown, URL, HTML, and renderer boundaries.
- CommonMark and product-specific adversarial fixture sources are licensed for use.

## Required decisions

Accept decision records for:

- Exact CommonMark version and enabled extension set
- Structural fingerprint schema and versioning
- Eligible inline contexts and context-specific escaping
- Reference definition, link, image, autolink, and raw HTML policy
- Behavior for unsupported syntax inside and outside otherwise eligible blocks
- Source encoding, byte-order mark, newline, and final-newline policy
- Capability identifiers and graduation process for new Markdown features

## Preservation contract

For an advertised supported input:

1. The source is valid UTF-8 within the configured size bound.
2. Every rewrite unit maps to non-overlapping half-open UTF-8 byte ranges.
3. Only approved ranges may change.
4. Generated text is escaped for its exact parser context.
5. Output reparses under the same dialect and extension configuration.
6. The versioned structural fingerprint remains equivalent.
7. All bytes outside approved ranges remain identical.
8. Protected destinations, labels, code, HTML, and unsupported constructs remain
   unchanged.

If any condition cannot be established, the adapter protects the affected content
or abstains with an actionable capability reason.

## Ordered work packages

### 1. Define the dialect and capability matrix

- Pin the CommonMark specification revision and parser configuration.
- Enumerate every enabled extension and its exact parser version.
- Assign stable capability IDs to block and inline features.
- Mark each feature as supported, protected, unsupported, or rejected.
- Record whether unsupported syntax causes unit-level protection or document-level
  abstention under each atomicity policy.
- Keep renderer-specific behavior outside the support claim unless separately
  qualified.

The first supported subset is plain inline prose in paragraphs and headings. Code,
raw HTML, links, images, autolinks, reference definitions, and complex inline
formatting remain byte-identical and ineligible until their own fixtures pass.

### 2. Build parser conformance fixtures

- Import the relevant official CommonMark examples under a documented fixture
  policy.
- Add CRLF, byte-order mark, final-newline, combining-character, bidi, invisible,
  invalid-boundary, and large-input cases.
- Add delimiter runs, escapes, entities, inline HTML, nested brackets, references,
  code spans, fenced code, indented code, lists, block quotes, thematic breaks,
  autolinks, and extension interactions.
- Add cases where a local edit changes a global reference or block parse.
- Record expected capabilities and eligibility independently from expected rewrite
  output.

Parser upgrades run the entire fixture set and produce a reviewed compatibility
diff before activation.

### 3. Produce adapter-owned parse state

- Use parser source offsets only as anchors, not as a lossless syntax tree.
- Build a versioned structural event fingerprint from block and inline roles,
  protected destinations, and relevant parser state.
- Derive non-overlapping rewrite units only from the approved subset.
- Keep format-specific tokens and source anchors in opaque adapter state.
- Validate parent, child, source-range, ordering, overlap, and UTF-8 boundaries at
  parse time.
- Report detected and unsupported capabilities before any model work.

The core document representation receives rewrite units and opaque anchors. It does
not interpret Markdown syntax.

### 4. Protect dangerous and ambiguous content

- Mark code spans, code blocks, raw HTML, link destinations, image destinations,
  reference definitions, autolinks, and extension syntax as protected.
- Preserve original HTML bytes and never render them inside application surfaces as
  trusted markup.
- Treat URLs and labels as typed invariants even when their visible text is eligible
  in a later capability.
- Detect parser ambiguities, overlapping event offsets, and constructs whose meaning
  depends on content outside the local block.
- Refuse generated text containing disallowed control or bidi characters.

Protection is established before prompt construction and verified again after
reparse.

### 5. Implement edit planning

- Translate accepted rewrite-unit changes back to approved source ranges.
- Require each edit to reference the parsed source digest and adapter-state version.
- Reject overlap, stale anchors, unsorted spans, invalid UTF-8 boundaries, and edits
  outside eligible capabilities.
- Calculate expected untouched byte ranges before mutation.
- Apply edits from greatest to least byte offset.
- Bound replacement bytes and total output growth.

No generated candidate receives direct access to source offsets or adapter state.

### 6. Implement context-specific escaping

- Escape punctuation only for the exact inline context and dialect.
- Prevent generated text from creating headings, lists, block quotes, code,
  emphasis, links, images, HTML, references, or extension syntax.
- Preserve user-authored entities and escapes when they are outside the approved
  range.
- Reject a candidate when safe escaping would materially alter the intended text or
  cannot be reversed unambiguously.
- Reparse every escaped candidate before it can be accepted.

Escaping is a safety transformation, not permission to expand the supported syntax
matrix.

### 7. Verify reassembly

- Reparse output using the same pinned parser configuration.
- Compare the versioned structural fingerprint.
- Compare protected literal, destination, code, HTML, and reference inventories.
- Verify byte identity outside planned edit ranges.
- Verify newline kind, byte-order mark, and final-newline policy.
- Reject newly executable or newly parsed syntax.
- Return the original bytes under document-atomic policy on any verification failure.

Verification failures have stable adapter and capability reason codes and retain no
partially written output.

### 8. Add properties, differential checks, and fuzzing

Properties include:

- Parse then apply no edits returns identical bytes.
- Approved edit application cannot modify an untouched range.
- Every produced span is an ordered UTF-8 boundary inside the input.
- Reordering independent edits does not change the output plan.
- Unsupported constructs never become eligible through adjacent content changes.
- Parse, serialize fixture metadata, and reparse preserve capability results.

Differential tests compare expected CommonMark behavior across parser upgrades, not
across renderers with different dialects. Fuzz targets cover parsing, eligibility,
edit planning, escaping, reparse, fingerprinting, and output growth bounds.

Every crashing or false-preservation input becomes a minimized regression fixture.

### 9. Integrate with the application and CLI

- Probe media type conservatively and allow explicit format selection.
- Show detected capabilities before rewriting in diagnostic mode.
- Report protected and unsupported regions without printing their content.
- Keep model and profile logic identical to plain text after rewrite units are
  produced.
- Add Markdown-specific `check`, rewrite, diff, dry-run, trace, output, and atomicity
  process tests.
- Make in-place writes opt-in, recoverable, and independent from adapter success.

Plain text remains available when a file has no Markdown intent. The application
does not silently reinterpret an unsupported Markdown document as plain text when
that would weaken structure protection.

### 10. Graduate features one at a time

For every proposed feature:

1. Add official, positive, negative, malformed, adjacent, and interaction fixtures.
2. Define eligible spans and exact protected state.
3. Define context escaping and structural fingerprint behavior.
4. Add property and fuzz coverage.
5. Run all prior features for regression.
6. Update the capability matrix and user documentation.
7. Record qualification evidence before changing its status to supported.

Candidate later features include simple emphasis or visible link text. Nested inline
formatting, raw HTML, extension interactions, and globally coupled references remain
late because they carry higher false-preservation risk.

## Security acceptance

- Raw HTML is never generated, changed, executed, or trusted.
- Link and image destinations cannot be introduced or changed by a prose rewrite.
- Generated text cannot create a new executable or renderer-active construct.
- Parser and output size, nesting, events, units, edits, and processing time are
  bounded.
- Source text and protected content remain absent from default logs and errors.
- Output verification uses the same dialect identity as parsing.
- A parser upgrade cannot silently change the advertised capability matrix.

## Required test matrix

| Area | Required evidence |
| --- | --- |
| Dialect | Pinned CommonMark examples and every enabled extension interaction |
| Encoding | UTF-8 boundaries, byte-order mark, LF, CRLF, final newline, Unicode normalization, and invalid input |
| Eligibility | Each supported, protected, unsupported, and rejected construct in isolation and adjacency |
| Escaping | Every delimiter and block-introducing character in every eligible context |
| Verification | Fingerprint changes, protected target changes, non-target byte changes, and stale adapter state |
| Security | HTML, executable links, controls, bidi, resource exhaustion, and malicious nesting |
| Platform | File paths, line endings, in-place safety, output replacement, and CLI behavior on all target systems |

Adapter parse, plan, apply, and verify paths target at least 90 percent line coverage
with every material branch represented. Overall Rust line coverage remains at least
80 percent.

## Exit evidence

The phase closes only when:

- Every advertised fixture preserves structure and non-target bytes exactly.
- No supported case introduces executable Markdown or changes a protected target.
- Unsupported syntax receives no false preservation claim.
- Parser upgrade detection and capability migration tests pass.
- CLI behavior passes on Windows, macOS, and Linux.
- The support matrix, limitations, and examples match implemented behavior.
- All four refinement passes are complete with no open critical structure, security,
  or data-loss defect.

The handoff to 0.5 includes a versioned adapter capability set, structural
fingerprint, adversarial corpus, and format-independent validation records that can
be used to calibrate risk without teaching strategies how to bypass adapter gates.
