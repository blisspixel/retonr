# 0.3 profile and CLI alpha execution plan

## Status and outcome

Status: planned after the 0.2 exit gate.

The phase outcome is an inspectable, versioned personal style profile with complete
non-voice CLI workflows. The profile must improve owner preference over the strongest
simple prompt or retrieval baseline without a material fidelity regression.

The profile is evidence plus declared policy, not an opaque persona prompt. The user
can inspect why a tendency exists, override it, exclude its evidence, restore an
earlier version, export it, and delete it.

## Entry criteria

- The grounded plain-text path and complete CLI meet the 0.2 gate.
- Exact generation and evaluator artifacts are qualified. Embedding candidates have
  immutable manifests and completed source and license review, and the generic
  headless artifact lifecycle is available for their qualification in this phase.
- Product-validation participants have authorized corpora and held-out material.
- Consent, retention, deletion, and adjudication protocols are approved.
- The application service can inject storage, time, randomness, and inference ports
  for deterministic tests.

## Required decisions

Accept decision records for:

- Profile and evidence schema versioning
- SQLite migration, backup, recovery, and concurrency policy
- Portable export schema and sensitivity labeling
- At-rest encryption and key recovery across desktop and headless environments
- Interpretable feature set and minimum evidence rules
- Embedding model, vector representation, invalidation, and reindex policy
- Retrieval eligibility, diversity, redaction, and leakage controls
- Declared-rule precedence and conflict resolution
- Derivative evidence and user feedback policy
- Profile identity, immutable version digest, and local equality identifiers

Encryption remains an explicit claim gate. The product does not imply encrypted
storage until every selected platform and recovery path is implemented and tested.

## Profile model

Keep source evidence, derived observations, declared rules, and compiled views
separate:

```text
Authorized evidence
  -> normalized evidence record
  -> independently versioned extractors and embeddings
  -> observed feature distributions with uncertainty
  -> declared rules and conflicts
  -> channel overlay with sparse-data fallback
  -> immutable compiled profile version
  -> retrieval view and generation view
```

Generated candidates never enter authorized evidence. Acceptance without edits is a
preference event only. User-edited generated text is derivative evidence and requires
explicit confirmation before it can have capped influence.

## Ordered work packages

### 1. Define evidence provenance

Each evidence record includes:

- Versioned evidence ID and source digest
- Source kind and import method
- Ownership or authorization confirmation
- Original channel, communicative act, locale, and optional date
- User-confirmed topic labels or a versioned, correctable topic-assignment artifact
  with its own provenance and confidence
- Relationship to a source document or derivative rewrite
- Consent, retention, retrieval eligibility, and profile-influence state
- Intrinsic byte count
- Creation, exclusion, and deletion audit metadata without raw-text logging

Token counts, extractor identities, and embedding identities belong to immutable
derived records, not intrinsic evidence metadata. Each token count binds to the exact
tokenizer artifact, runtime, input instruction, preprocessing, truncation policy, and
limits that produced it.

The schema distinguishes raw evidence text from metadata and derived features. It
defines four distinct states:

- `retrieval_ineligible`: exclude the item from example retrieval and active
  retrieval snapshots while retaining separately approved aggregate observations.
- `influence_excluded`: retain source metadata according to policy, but invalidate
  the item's complete active derivation closure and exclude it from retrieval and all
  future compiled profile influence.
- `consent_revoked`: stop all permitted use, invalidate the complete derivation
  closure, and remove application-controlled material according to the approved
  retention and legal policy.
- `deleted`: invalidate the complete derivation closure and remove the item from
  application-controlled active storage, indexes, caches, and backups in scope.

Validation rejects malformed IDs, unknown source kinds, invalid provenance graphs,
cycles, missing consent, oversized samples, duplicate imports, and inconsistent
deletion state.

### 2. Build migration-safe storage

- Use SQLite transactions and foreign-key enforcement.
- Apply forward-only schema migrations and record application version and checksum.
- Test migration from every released schema, not only the immediately prior one.
- Make profile version creation atomic and immutable.
- Keep raw evidence, derived features, vectors, rules, and rewrite metadata in
  separate tables with explicit ownership.
- Define SQLite freelist, write-ahead log, temporary file, backup, crash-dump, and
  swap exposure. Use cryptographic erasure when selected encryption permits it and
  document operating-system and storage-device limits.
- Move blocking database work off async executors.
- Define connection, busy-timeout, cancellation, pre-migration backup, verified
  restore, and corruption behavior.
- Use application directories from platform APIs.
- Never hide a destructive reset behind an automatic migration failure fallback.

Every migration has forward, reopen, interrupted-transaction, pre-migration backup,
verified backup-restore rollback, and deletion fixtures on Windows, macOS, and Linux.
Automatic down migrations are not supported unless a later decision record defines
and qualifies a specific case.

### 3. Implement evidence ingestion

- Accept explicit files and directories through bounded readers.
- Detect duplicates by approved local identity without calling the result anonymous.
- Segment samples by source document and communicative unit while retaining source
  anchors.
- Normalize only the representation needed for analysis. Preserve the authorized raw
  sample separately when retention is enabled.
- Detect low-information, boilerplate-dominated, generated, mixed-author, or
  unsupported samples and request review rather than silently weighting them.
- Let the user confirm or correct topic assignment before it affects contribution
  caps or topic-held-out evaluation.
- Apply per-document and per-session contribution caps before compilation.
- Preview additions, exclusions, and resulting profile changes before activation.

Directory traversal, symlink, permission, non-UTF-8 path, case-collision, and partial
failure behavior is explicit and tested.

### 4. Extract interpretable observations

Start with observable features that users can understand and correct, such as:

- Sentence and paragraph length distributions
- Contraction and abbreviation tendencies
- Punctuation and capitalization patterns
- Heading, list, salutation, sign-off, and transition behavior
- Preferred directness, hedging, modality, and first-person usage
- Vocabulary and phrase preferences after sensitive and topical filtering
- Channel-specific formatting and register

Every observation records extractor version, sample count, uncertainty, evidence
IDs, channel coverage, and stability across held-out samples. The compiler enforces a
minimum evidence threshold and does not present a weak estimate as a user fact.

Topic-held-out tests determine whether an observation captures style or merely
content. Sensitive tokens, names, identifiers, and quantities are not promoted into
style preferences.

### 5. Add declared rules and conflict detection

Rules use typed predicates and actions rather than free-form prompt fragments where
possible. Each rule includes:

- Scope and channel
- Enforcement: require, prefer, avoid, or forbid
- Priority and origin
- Examples and counterexamples
- Version and activation state
- Conflict evidence

Fidelity and format obligations always outrank style rules. Explicit active rules
outrank inferred tendencies. More specific channel rules outrank general rules only
when they do not weaken a higher obligation.

The compiler rejects unresolved hard conflicts and reports a minimal conflict set.
Complete precedence and shadowing tables are covered by deterministic tests.

### 6. Compile immutable profiles

- Compile from a declared set of evidence, extractor outputs, rules, models, and
  compiler version.
- Produce a content-addressed immutable version plus a human-readable change summary.
- Cap influence per source, session, and topic.
- Use hierarchical channel fallback so sparse channels shrink toward the general
  profile instead of overfitting.
- Store uncertainty and minimum-sample decisions with the compiled result.
- Keep generation, retrieval, and presentation views derivable from the same
  versioned source record.
- Make restore create a new active pointer or version, never mutate history.
- Invalidate every derived observation, vector, rule dependency, retrieval snapshot,
  and compiled view in the transitive derivation closure of influence-excluded,
  consent-revoked, or deleted evidence. Retrieval-ineligible evidence invalidates
  only retrieval indexes and snapshots.

Repeated compilation from identical authorized inputs and exact artifacts must be
deterministic. Any probabilistic extraction occurs before compilation and is stored
as an immutable derived artifact with source evidence IDs, artifact and runtime,
parameters, seed or randomness policy, relevant execution environment, and output
digest. Compilation consumes persisted derived artifacts and never reruns inference.

### 7. Qualify the embedding space

- Set `truncate: false` and reject oversized input explicitly.
- Define one canonical `embedding_space_id` over the exact artifact, runtime,
  dimensions, input instruction, preprocessing, normalization, truncation, byte and
  token limits, distance, quantization, and serialization identity.
- Reject non-finite values, wrong dimensions, unexpected normalization, and malformed
  batches.
- Compare singleton and batch output within a predeclared tolerance.
- Recheck the complete artifact and runtime identity immediately before and after
  every batch. Discard the complete batch on drift, invalidate the active
  `embedding_space_id` qualification, and require explicit requalification and
  reindexing.
- Measure repeatability, latency, memory, and cancellation on declared hardware.
- Benchmark task-specific style retrieval against metadata-only, lexical, and
  interpretable-feature baselines.
- Test same-owner cross-topic retrieval and topic prediction from embedding vectors.
- Invalidate and rebuild stored vectors when any embedding-space identity changes.

No production vector is created until the exact embedding space passes these gates.

### 8. Implement leakage-resistant retrieval

Before implementation, define a versioned leakage policy with rare and unique phrase
criteria, corpus-frequency rules, handling for spans already present in the source,
entity and quantity novelty rules, severity, and per-category pass thresholds.

- Filter by profile version, channel, communicative act, authorization, retention,
  and eligibility before scoring.
- Combine lexical and embedding signals only after each has an independently tested
  purpose.
- Prioritize structural and style relevance over topical similarity.
- Enforce maximum examples, bytes, tokens, and contribution per source document.
- Diversify across documents and topics.
- Redact or mask sensitive strings, entities, identifiers, URLs, and quantities in
  retrieved examples where the task permits.
- Track every retrieved evidence ID in the rewrite record.
- Reject leakage according to that policy and record the matching evidence IDs
  without storing sensitive matched text in default traces.
- Run canary, cross-profile, rare-phrase, unique n-gram, entity, and quantity
  extraction fixtures.

The initial personal corpus uses FTS5 and filtered vector scoring in Rust. A vector
database is not introduced without measured scale or latency evidence.

Any field change in the canonical `embedding_space_id` invalidates every affected
vector. Reindex is explicit, resumable, and cancelable.

### 9. Add typed acquisition workflows

- Implement structured interviews and scenario prompts before voice.
- Ask only questions tied to a profile uncertainty or user goal.
- Explain how an answer will affect rules or evidence.
- Let the user skip, revise, compare, and remove every answer.
- Keep answers provisional until the user previews and activates the profile change.
- Use the same evidence schema later used by voice transcripts.
- Prevent one interview session from dominating the profile.

The workflow works entirely through the CLI and never requires an editor, desktop
application, or microphone.

### 10. Complete profile CLI workflows

Implement and test:

- Create, list, inspect, compare, and select
- Ingest with preview and authorization confirmation
- Typed interview
- Rule add, edit, disable, and conflict resolution
- Evidence inspect, mark retrieval-ineligible, exclude from profile influence,
  restore eligible retained evidence, revoke consent, and delete
- Version compare, activate, and restore
- Export, import, validate, and migrate
- Full profile deletion and verification report
- Reindex and diagnostic commands

Machine output uses provisional versioned schemas and stable categories. Human
output explains evidence, uncertainty, conflicts, and recovery without exposing raw
content in logs. Non-interactive commands never prompt and require explicit flags for
authorization or destructive changes.

### 11. Implement feedback without contamination

Feedback events distinguish:

- Accepted unchanged
- Accepted after user edit
- Rejected for style
- Rejected for fidelity concern
- Candidate comparison preference
- Rule correction

An event can update evaluation or preference statistics without becoming corpus
evidence. Derivative text requires explicit authorization, retains lineage, and has
capped weight. No implicit feedback changes an active profile version.

Tests prove that raw candidates, merely accepted outputs, and unconfirmed derivative
text cannot enter retrieval or compiled observations.

### 12. Validate portability and deletion

- Export a versioned manifest with sensitivity warning, evidence inclusion choices,
  checksums, model dependencies, and migration range.
- Do not export executable configuration, credentials, arbitrary filesystem paths,
  or service authority.
- Validate import in a restricted schema before writing to the active store.
- Preview imported rules, conflicts, evidence, artifact gaps, and migrations.
- Remove evidence, vectors, derived observations, profile versions, traces, and
  retained audio references from application-controlled active storage and indexes.
- Verify transitive derivation-closure invalidation before reporting deletion or
  influence exclusion complete. Verify retrieval snapshot invalidation separately
  for retrieval-ineligible evidence.
- Explain that external backups and exported files require separate deletion.

Deletion tests inspect the database, write-ahead log, temporary files, indexes,
application backups, and application directories, not only the user interface
result. Reports distinguish logical deletion, application-controlled storage cleanup,
cryptographic erasure where available, and data that may remain in user backups,
operating-system caches, crash dumps, swap, or storage-device recovery.

### 13. Run product validation

- Register the minimum meaningful preference effect, fidelity non-inferiority bound,
  power or precision calculation, participant and paired-task counts, minimum per
  channel, multiplicity policy, repeated-measures analysis, and missing-data handling.

Compare at least:

- No rewrite
- Direct prompt
- Explicit style description
- Retrieved examples
- Compiled interpretable profile
- Any compact adapter experiment that fits the declared hardware and consent policy

Use held-out topics and owner-written references. Blind and randomize candidate
presentation. Report owner preference with fidelity false acceptance, coverage,
abstention, edit cost, leakage, latency, memory, and onboarding burden.

Pre-register measurable thresholds for topic prediction from style representations,
same-owner cross-topic retrieval, topic-held-out preference, rare-phrase copying,
canary extraction, and cross-profile extraction. A result is insufficient evidence
rather than a pass when the required sample size is not met.

Predeclare what constitutes a meaningful preference improvement and a material
fidelity regression. If the compiled approach does not beat the strongest simple
baseline, simplify or stop the profile architecture before building more surfaces.

## Security and privacy acceptance

- Imported samples and profile files are untrusted and bounded.
- Profile mutation requires stronger authority than rewriting.
- The generator cannot mutate evidence, rules, or active versions.
- Portable profiles contain no credentials or service configuration.
- Logs and default traces omit evidence text and retrieved examples.
- Retrieval-ineligible evidence cannot appear in retrieval results but may retain
  separately approved aggregate influence.
- Influence-excluded, consent-revoked, and deleted evidence cannot appear in new
  retrieval results or compiled versions and invalidates its complete transitive
  derivation closure.
- Backup, recovery, and encryption behavior is accurate on Windows, macOS, and Linux.
- Authorization and provenance cannot be removed through import or migration.

## Required test matrix

| Area | Required evidence |
| --- | --- |
| Schema | Round trips, malformed data, old versions, unknown fields, bounds, and invariant enforcement |
| Migrations | Every released version, interruption, pre-migration backup, verified restore rollback, corruption, and platform paths |
| Compiler | Determinism, contribution caps, sparse channels, uncertainty, conflicts, and restore behavior |
| Embeddings | Truncation off, dimensions, finite values, normalization, batch consistency, bounds, repeatability, complete artifact and runtime identity drift, invalidation, latency, and task quality |
| Retrieval | Eligibility, diversity, topic holdout, policy thresholds, canaries, cross-profile extraction, redaction, bounds, cancellation, and reindex |
| Feedback | No candidate contamination, derivative lineage, explicit activation, and deletion |
| CLI | Interactive and non-interactive behavior, machine schemas, confirmation, recovery, and redaction |
| Product | Blind owner preference, fidelity, coverage, leakage, resource use, and onboarding completion |

Overall Rust line coverage remains at least 80 percent. Storage migrations,
authorization, deletion, rule precedence, compiler decisions, and retrieval filters
require every material branch to be represented.

## Exit evidence

The phase closes only when:

- Users can complete every non-voice profile workflow from the CLI.
- Blind held-out evaluation passes the predeclared product threshold.
- Predeclared topic-confounding, cross-topic retrieval, and topic-held-out thresholds
  pass with sufficient evidence.
- Every category in the versioned leakage policy passes its predeclared threshold,
  including rare and unique phrases, entities, quantities, canaries, and
  cross-profile extraction.
- Generated candidates never become evidence.
- Export, import, migrate, restore, reindex, and delete pass on all target systems.
- Encryption and key-recovery documentation matches tested behavior, or the product
  clearly reports that storage is not encrypted.
- The strongest simple baseline remains in the regular regression suite.
- All four refinement passes are complete with no open critical privacy, fidelity,
  migration, or data-loss defect.

The handoff to 0.4 includes a stable profile read port, immutable version identity,
retrieval bounds, leakage checks, and complete plain-text behavior independent of any
document-format adapter.
