# 0.2 evidence closure and CLI batch

## Purpose and budget

This development batch advances the existing plain-text milestone through three
independent components. It uses repository fixtures and local tooling with no paid
services, model downloads, or new production policy roots. External spending for
this batch is $0 against a $20 ceiling.

The [current-state document](../current-state.md) records implemented behavior.
This plan defines requirements and acceptance evidence; it does not confer runtime
admission, generation qualification, or a release claim.

## Why these components come next

The CLI already validates and inspects documents, and the libraries already model
managed generation and qualification evidence. The immediate gap is connecting
those contracts to exact retained bytes and durable relationships. Adding another
format or presentation layer would inherit that gap.

| Component | Work | Acceptance evidence |
| --- | --- | --- |
| Candidate receipt-set settlement | Match a live target batch set to the sealed operation ledger, persist its exact portable receipt set, and independently read it back | Reject missing, duplicate, substituted, baseline, cross-operation, and wrong-repetition evidence; reconstruct semantic suite order and preserve cancellation, deadlines, and finalization |
| Runtime-admission bundle verification | Reacquire an exact bounded evidence tree, verify its canonical manifest and foundation, retain its directory identity, and detect later drift | Reject altered bytes, unexpected or missing entries, aliases, noncanonical records, resource-limit violations, and cancellation; keep diagnostics content-redacted |
| Directory editorial lint | Reuse bounded document discovery for deterministic folder reports and apply the existing terminal-safety contract | Process-level fixtures for recursion, exclusions, ordering, per-file outcomes, candidate conflicts, policy exit status, hostile controls, and unchanged inputs |

The receipt-set component belongs to the evaluation operation boundary. The bundle
verifier belongs to the application evidence boundary. Directory lint belongs to
the CLI and reuses existing editorial rules and source discovery. These ownership
boundaries allow implementation to proceed independently without duplicating
product validation.

Resource review of directory lint also covers the shared scanner and comparative
report. Dense repeated punctuation must not overflow the occurrence counter or
rescan the full prefix for every match. Comparison must account for repeated
findings as a multiset, so reducing three equal defects to one reports two resolved
and one retained. Saturated occurrence identifiers must preserve multiplicity.

## Verification

Run focused regression tests while implementing each component, then integrate the
batch through workspace formatting, strict Clippy, all-target and all-feature
checks, workspace and documentation tests, repository policy, and Markdown lint.
Run Linux coverage with the repository's 80 percent line floor and retain the
result. Native isolation and supported-platform release checks remain separate
requirements where this local environment cannot reproduce the full CI matrix.

Review the integrated changes for stale documentation, exported authority,
unbounded reads, terminal control injection, source mutation, and accidental
fallback. Stored evidence and a verified byte closure cannot recreate process-local
execution authority.
