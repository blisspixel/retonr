# 0.9 contract freeze and release qualification execution plan

## Status and outcome

Status: planned. This is the first compatibility-freeze and full release-
qualification phase; earlier phases remain iterative.

The phase outcome is the smallest complete product contract frozen, packaged, and
qualified from exact release artifacts on Windows, macOS, and Linux. It adds no new
major product surface. Any feature that cannot meet the gates remains preview,
experimental, narrower, or post-1.0.

Local voice is not a 1.0 dependency. It remains a later optional acquisition mode
after typed profiles, the native desktop, artifact licensing, accessibility, and
deletion behavior are already proven.

## Entry criteria

- CLI, profiles, Markdown, calibration, runtime paths, agent packages, DOCX, document
  transactions, and native desktop pass their phase gates.
- Every candidate stable contract has an owner, version, compatibility policy,
  malformed-input suite, and migration range.
- Exact supported operating-system, architecture, runtime, artifact, execution,
  format, language, protocol, client, and package matrices are approved.
- Security, privacy, legal, license, accessibility, distribution, and support
  limitations are reviewed for the release candidate.
- No feature relies on a floating specification, dependency, model tag, schema,
  installer source, or update identity.

## Required decisions

Accept final release decisions for:

- Stable contract versions and compatibility ranges
- Rust shipping feature manifests per binary and target
- Platform floors, architectures, installers, package formats, and update channels
- Artifact signing, key custody, revocation, loss, and recovery
- Reproducible unsigned payload boundaries and comparison policy
- Software bill of materials, provenance, checksum, and attestation formats
- Support matrix, deprecation policy, security disclosure, and maintenance process
- Final privacy, diagnostics, crash, history, and residue behavior
- Name, namespace, package, model, runtime, and third-party license clearance

## Ordered work packages

### 1. Freeze the supported product matrix

List exact:

- Rust target triples, operating-system floors, architectures, package formats, and
  minimum hardware classes
- Runtime packages, artifact sets, tokenizers, templates, parameters, languages,
  strategies, formats, and execution classes
- Ollama, llama.cpp, LM Studio, vLLM, and MLX LM status as qualified, experimental,
  unsupported, or not applicable, with retained native evidence and exact reasons
- CLI, profile, record, document, API, MCP, Agent Skill, Agent Plugin, and native
  desktop versions
- Named agent clients and exact compatible versions
- Qualified context envelopes, input sizes, unit counts, document sizes, archive
  limits, concurrency, deadlines, memory, and disk requirements
- Explicit unsupported and experimental combinations

No family name, generic operating-system label, compatible API label, or mutable tag
stands in for an exact row.

### 2. Freeze stable contracts

- Promote proven preview schemas to stable versioned paths.
- Freeze CLI grammar, machine output, exit categories, configuration precedence,
  profile and evidence schemas, rewrite records, qualification records, document
  capabilities, change reports, MCP tools, Agent Skill content, Agent Plugin
  manifests, local API resources, and compatibility adapter behavior.
- Retain old fixtures and run old-consumer and new-implementation tests where that
  compatibility is promised.
- Classify every contract change as compatible, migrated, parallel-versioned, or
  intentionally breaking.
- Reject unknown stable versions and unsafe downgrade paths deterministically.

Rust API semantic-version checks apply only to crates deliberately published as
supported libraries. Behavioral fixtures remain authoritative for non-Rust
contracts.

### 3. Close the Rust engineering baseline

- Test exact default, no-default, shipping, and all-feature configurations.
- Exclude test support, fuzz hooks, diagnostic adapters, and instrumented UI hooks
  from shipping features.
- Run warnings-denied builds, Clippy, rustdoc, unit, integration, process, property,
  coverage, mutation, Miri, fuzz, and sanitizer gates as applicable.
- Enable checked arithmetic and release-profile black-box coverage at untrusted size,
  offset, allocation, archive, and document boundaries.
- Quarantine every native or unsafe dependency behind reviewed adapters and safe
  interfaces.
- Retain exact compiler, linker, target, features, dependency graph, and commands.

The complete standard and primary sources are in
[Rust engineering and release research](../research/2026-08-12-rust-engineering.md).

### 4. Close dependency and source supply chains

- Resolve or explicitly accept advisories, licenses, duplicates, sources, build
  scripts, procedural macros, native libraries, model artifacts, and conversion tools.
- Maintain Cargo Vet policy with reviewed audits and bounded exemptions.
- Produce a vendored source bundle with license material.
- Prove frozen no-network builds for the exact shipping targets and features.
- Embed or bind exact binary dependency metadata.
- Generate a per-artifact software bill of materials.
- Rehash runtime, model, tokenizer, template, adapter, and document-test artifacts at
  release input and installed state.

A clean lockfile, signature, or advisory scan alone is not a supply-chain claim.

### 5. Produce reproducible unsigned artifacts

- Remove wall-clock, random-order, host-path, username, hostname, and undeclared
  network inputs where possible.
- Define reproducibility separately for compiled binaries, package payloads,
  archives, signatures, notarization, and update metadata.
- Build each unsigned target twice in isolated clean environments from the same
  declared source and inputs.
- Compare bytes where possible and use a reviewed structural comparison only for
  documented unavoidable package fields.
- Treat every unexplained difference as a release blocker.
- Bind debug or support symbols separately to exact binary digests where supported.

### 6. Sign and attest release artifacts

- Sign only payloads that passed comparison and qualification.
- Record unsigned, signed, notarized, stapled, packaged, and update derivative digests
  separately.
- Generate provenance from the hosted build control plane and bind source, workflow,
  builder, compiler, target, features, dependencies, and outputs.
- Keep signing secrets outside ordinary build steps.
- Publish checksums, signatures, provenance, software bills of materials, support
  matrix, and verification instructions together.
- Test public verification instructions on clean supported systems.

### 7. Rehearse installation and lifecycle

For each supported package:

- Clean install through the documented no-admin and inspect-first paths
- Exact-version install and invalid-version rejection
- Offline model import and offline core operation
- Interrupted download, install, model import, document transaction, update, and
  migration recovery
- Update from every retained supported version
- Downgrade rejection or documented recovery
- Profile, history, model, staged output, configuration, and plugin migration
- Uninstall and application-controlled residue inspection
- Lost updater access, invalid signature, corrupted package, low disk, read-only
  destination, and partial package failure

The source document and profile remain recoverable across every failure fixture.

### 8. Run locked product qualification

Use exact signed release candidates and frozen data to run:

- Fidelity false acceptance, transformation coverage, abstention, style preference,
  leakage, and calibration
- Long-document beginning, middle, end, boundary, consistency, context, cancellation,
  and change-report fixtures
- Markdown and DOCX structure, package, untouched-state, reopen, and render evidence
- Runtime, artifact, quantization, accelerator, language, and execution differential
  suites
- CLI, agent, plugin, MCP, API, compatibility adapter, desktop, and cross-interface
  equality
- Accessibility, international text, keyboard, screen-reader, contrast, scale, and
  reduced-motion review
- Latency, memory, disk, energy where measured, sustained operation, and resource
  exhaustion
- No-network, logging, diagnostics, history, deletion, and privacy behavior

Results are published together. A style win cannot conceal a fidelity failure, and a
passing aggregate cannot conceal a failed support row.

### 9. Audit every invariant

For every invariant in
[Product and engineering invariants](../invariants.md), retain:

- Applicable or not-applicable disposition
- Test, decision, review, or qualification artifact
- Exact revision and release artifact digest
- Known limitation and follow-up trigger

An invariant with neither evidence nor a defensible not-applicable rationale blocks
promotion.

### 10. Publish accurate product evidence

- Update current state from exact release evidence.
- Ensure README, install instructions, help, manual pages, schemas, examples,
  screenshots, and limitations match the release binaries.
- Use synthetic content in public captures.
- State the editorial sovereignty and legal-responsibility boundary without claiming
  legal advice, authorship proof, or universal watermark removal.
- Publish known failures and deliberately unsupported combinations.
- Remove stale planned claims and experimental flags from stable presentation.

## Required release matrix

| Gate | Required evidence |
| --- | --- |
| Contracts | Compatibility diffs, retained old fixtures, migrations, downgrade behavior, and malformed input |
| Rust | Exact features, warnings, lint, docs, tests, coverage, property, mutation, Miri, fuzz, sanitizers, and release-profile behavior |
| Supply chain | Lockfile, audits, vetting, licenses, vendored source, binary metadata, SBOM, checksums, and provenance |
| Reproducibility | Independent unsigned rebuilds, comparisons, documented normalized fields, and derivative digests |
| Platform | Clean install, offline operation, update, recovery, migration, removal, accessibility, and packaging |
| Product | Fidelity, style, leakage, formats, long documents, runtimes, agents, desktop, privacy, and performance |
| Governance | Threat model, legal review, editorial policy, security disclosure, name clearance, and limitations |

## 1.0 promotion gate

Version 1.0 is promoted only when:

- Every required capability in the roadmap passes its exact support matrix.
- No open critical security, fidelity, data-loss, privacy, accessibility, license,
  packaging, migration, compatibility, or update defect remains.
- All stable contracts pass backward-compatibility suites.
- Overall implemented Rust line coverage is at least 80 percent and critical paths
  meet higher targets.
- Formatting, strict linting, documentation, policy, tests, dependencies, advisories,
  licenses, fuzzing, mutation, packages, platform jobs, and release verification pass.
- Signed artifacts install and operate offline after explicit artifact setup or
  offline import on every advertised platform.
- Every invariant has retained evidence or an accepted not-applicable rationale.
- Public documentation describes only implemented, qualified behavior.

Anything that misses this gate moves later or becomes narrower. Fidelity, source
preservation, user control, local privacy, accessibility, and honest uncertainty are
not weakened to preserve the release label.
