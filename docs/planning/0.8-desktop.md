# 0.8 desktop beta execution plan

## Status and outcome

Status: planned after the 0.7 exit gate.

The phase outcome is a secure, accessible Tauri desktop beta on Windows, macOS, and
Linux. It exposes the same application service as the CLI and adds no independent
rewrite, validation, model, profile, or document logic.

The desktop must make rewritten, unchanged, abstained, unsupported, cancelled, and
failed outcomes unmistakable. It must remain fully usable with keyboard and assistive
technology before voice is added.

## Entry criteria

- Application, profile, model, document, and integration contracts pass prior gates.
- The supported OS, architecture, WebView, minimum hardware, and package matrix is
  approved.
- A design-system and accessible component spike passes on every target WebView.
- Desktop authority, IPC, updater, signing, and key-recovery decisions are approved.
- Release evidence is defined before UI screenshots can be accepted.

## Required decisions

Accept decision records for:

- Tauri version, frontend framework, accessible primitives, and build tool
- Rust to frontend DTO generation and compatibility
- Tauri command registration, permissions, capability selection, and scope checks
- Window model and authority per window label
- Operation state, event ordering, cancellation, and stale-event handling
- Content security policy, external link policy, and isolation pattern evaluation
- Updater ownership, network consent, signing keys, rotation, backup, and recovery
- Native package formats and minimum platform versions
- Accessibility conformance method and supported assistive technologies
- Performance and visual-regression budgets
- Frontend Vitest and V8 coverage versions, source and branch semantics, reviewed
  exclusions, general and critical configurations, and CI artifact format
- Desktop end-to-end provider, test-only instrumentation feature, release dependency
  and capability audit, and external black-box signed-binary harness on each platform

## Component boundaries

```text
rewrite-app
  <- rewrite-desktop-bridge
  <- Tauri shell
  <- frontend feature modules

rewrite-speech and native audio remain absent until 0.9.
```

Rust owns filesystem access, profile mutation, rewriting, validation, audio in the
later phase, model management, and updater actions. The frontend owns presentation,
local form state, accessible interaction, and calls narrow typed commands.

The frontend receives no general filesystem, shell, process, database, HTTP, model,
or update authority. It never receives a raw database handle, filesystem root, model
service credential, or unscoped or durable profile mutation authority.

## Operation state contract

Every long-running command first creates a suspended operation and returns its ID,
owner window session, and initial snapshot. The frontend then subscribes with a
per-invocation Tauri channel. Rust validates ownership, installs the channel, returns
an acknowledgement snapshot, and only then starts work. Events are targeted to that
channel and carry operation ID and a contiguous monotonic sequence number. Frontend
reducers ignore stale, duplicate, out-of-order, or completed-operation events.

A sequence gap freezes presentation of new state and triggers a bounded snapshot
query with the last accepted sequence. The authoritative snapshot either resumes the
stream or reports a terminal outcome. A window close or reload revokes its operation
ownership and cancels its operations. Durable artifact-download staging may remain,
but resumption requires a new explicit command after reload. No operation or event is
delivered across window sessions, and global broadcast events are not used for
privileged work.

The shared discriminated state includes:

- Idle
- Preparing
- Running with a named stage and bounded progress
- Completed with rewritten, unchanged, or abstained outcome
- Unsupported
- Cancelled
- Failed with stable code and safe recovery actions

Cancellation is an application command, not a frontend-only state change. A visible
cancelled state appears quickly while Rust confirms cleanup and prevents late output
from replacing it.

## Ordered work packages

### 1. Create the shell with no product authority

- Add a minimal Tauri application that opens one local window.
- Bundle all frontend assets. Load no remote page, frame, script, font, style, or
  image.
- Configure a strict content security policy with no inline script or eval.
- Expose no shell, process, unrestricted opener, general HTTP, or general filesystem
  plugin.
- Keep update, dialog, and file behavior Rust-owned through narrow commands.
- Record WebView version and platform identity in redacted diagnostics.

The first signed smoke build performs no rewrite. It proves install, launch, close,
crash reporting policy, and absence of unexpected network access.

### 2. Lock Tauri capabilities and commands

- Explicitly list enabled capability identifiers in configuration.
- Register every custom command in the application manifest.
- Use one least-privileged capability per window label.
- Enumerate individual permissions and avoid broad defaults and wildcards.
- Implement application-level scope checks inside every privileged command.
- Deny unknown window labels, path scopes, operation IDs, profile IDs, and model IDs.
- Add a machine-readable authorization decision table.
- Audit merged capabilities because multiple capability files can broaden a window.
- Add negative authorization and configuration tests to continuous integration.

Because the first application uses one window, static Tauri capabilities establish
only its minimum command surface. Sensitive mutations use an application-issued,
opaque, expiring authority grant bound to the exact window session, profile or
resource, operation, and allowed action. Every Rust command validates the grant.
Frontend route state is presentation state and is never trusted for authorization.

The isolation pattern is evaluated after the primary boundary is correct. It is
defense in depth, not a replacement for narrow commands and scopes.

### 3. Generate one typed IPC contract

- Derive frontend DTOs and schemas from one reviewed Rust-owned contract.
- Keep wire DTOs separate from domain and persistence types.
- Deny unknown fields unless an explicit compatibility rule exists.
- Bound every string, list, map, byte reference, event, and error detail.
- Version commands and events that may outlive one desktop release.
- Translate domain outcomes without flattening abstention into an error.
- Fuzz command deserialization and event serialization.

Schema generation and checked-in outputs fail continuous integration when stale or
incompatible without an accepted migration.

### 4. Build the state and routing skeleton

- Organize frontend code by workbench, profile, models, history, settings, and shared
  presentation primitives.
- Use feature-local state and explicit application queries rather than one global
  catch-all store.
- Implement operation reducers with property tests for legal transitions.
- Restore only safe presentation state after restart.
- Never restore a recording, in-flight rewrite, unconfirmed mutation, or privileged
  dialog as active.
- Add route, focus, title, and dirty-state behavior before complex screens.

Production TypeScript files target no more than 350 nonblank lines and feature
components no more than 200, with documented exceptions. Responsibility and
dependency direction remain the primary split criteria.

### 5. Establish the design system

- Use accessible interaction primitives and a small product-owned visual layer.
- Define semantic tokens for color, typography, spacing, focus, border, target size,
  elevation, motion, protected content, success, warning, and failure.
- Use system fonts and local assets.
- Support light, dark, high-contrast or forced-colors, reduced-motion, and text zoom.
- Keep state understandable without color, motion, icons, or spatial position alone.
- Validate at 1024 by 600 and at 200 percent zoom without losing functionality.
- Respect platform menus, labels, accelerators, and dialog conventions.

Tab moves between components. Arrow keys operate composite widgets. DOM, reading,
visual, and focus order remain logical without positive `tabindex`.

### 6. Implement onboarding

- Explain local-first behavior and exact network state.
- Show model source, digest, license, size, language, hardware, qualification, and
  installation state.
- Require explicit model download or offline import.
- Collect corpus authorization and retention choices.
- Offer a complete typed interview and first held-out preview.
- Make every permission request just in time and explain its purpose.
- Provide recovery for missing runtime, unsupported hardware, insufficient disk,
  corrupt model, denied file access, and offline state.

Onboarding can be left and resumed without weakening consent or creating partial
profile evidence.

### 7. Implement the rewrite workbench

- Provide text entry and safe document selection.
- Show profile, channel, mode, format capability, and atomicity controls.
- Summarize protected content without exposing it in diagnostics.
- Present source and proposed output as text, never untrusted HTML.
- Offer side-by-side and accessible unified linear diff.
- Give each change a heading, original and proposed labels, next and previous
  navigation, and selectable text.
- Group validation evidence into exact, structural, semantic, and style categories.
- Provide copy, export, safe replace, undo, cancellation, and trace export.

Abstention is presented as a protected result such as "Original kept", followed by
stable category, affected structural location, what was verified, and safe next
actions. Raw model scores are not presented as calibrated certainty.

### 8. Implement the profile lab

- Show declared rules, observed features, uncertainty, sample counts, channels, and
  conflicts.
- Browse evidence metadata and provenance with explicit raw-content reveal.
- Preview rule, evidence, retrieval, and active-version changes.
- Compare and restore immutable versions.
- Export, import, and delete through the same application service as the CLI.
- Require a separate short-lived, window-bound application authority grant for
  profile mutation.
- Confirm destructive operations and provide a deletion verification report.

No frontend action can admit generated text as evidence without the application
service's explicit provenance and confirmation checks.

### 9. Implement the model manager

- List installed, missing, corrupt, unsupported, and qualified artifacts.
- Show source, exact digest, runtime, license, size, context, hardware, and supported
  roles.
- Support explicit download, resume, offline import, verify, qualify, and remove.
- Show expected network and disk activity before starting.
- Keep downloads and update checks off by default until explicitly initiated.
- Verify checksum and manifest before activation.
- Prevent removal while an operation owns the artifact and provide recoverable
  cleanup after interruption.

The frontend never sends arbitrary model-service URLs or commands.

### 10. Implement settings, diagnostics, and history

- Make network, storage, encryption, accessibility, motion, shortcut, model, and
  update policies explicit.
- Keep history opt-in and content-free by default.
- Provide bounded, redacted diagnostic export with a preview.
- Let users inspect and purge rewrite metadata, traces, cached artifacts, and profile
  data.
- Explain external backup and export limitations.
- Use native credential storage only through the approved Rust boundary.

Settings changes create versioned application policy and cannot silently broaden a
running operation's authority.

### 11. Implement native integration and packaging

Windows:

- Sign executable, installer, and update artifacts.
- Prefer evergreen WebView2 and offer a documented offline installer path.
- Test non-admin installation, per-user and machine scope where supported, upgrade,
  removal, file locks, long paths, scaling, and high contrast.

macOS:

- Build and sign on macOS, including every embedded binary and library.
- Notarize and staple Developer ID distribution.
- Build one qualified universal application containing Apple silicon and Intel
  slices, and test Gatekeeper launch with network blocked on both architectures.
- Follow native menu and Command-key conventions.

Linux:

- Publish exact distribution, library, package, and architecture support.
- Test selected packages on the oldest supported libraries.
- Test Wayland, X11, portals, desktop entry, themes, Orca, and uninstall residue.

Packages are built and smoke-tested on their target operating system.

WebdriverIO coverage that requires `tauri-plugin-wdio-webdriver` or
`tauri-plugin-wdio` runs only in a dedicated instrumented test build behind a
non-release Cargo feature. Release qualification proves through `cargo metadata`, the
resolved feature graph, capability manifests, bundle inspection, open-port checks, and
permission or entitlement inspection that both plugins and their authority are absent
from the signed release. The unmodified signed application receives a separate
black-box workflow run. On macOS, an external XCTest, accessibility, or equivalent
harness selected by the decision record launches the notarized bundle and exercises
install, launch, navigation, keyboard, accessibility, rewrite, cancellation, offline,
update, and close behavior without a WebDriver plugin.

### 12. Implement the updater as a separate authority

- Keep update checks explicit and off by default under the offline policy.
- Display endpoint, target version, download bytes, checksum, signature, and release
  notes before install.
- Make verification and install Rust-owned.
- Back up signing keys offline and document rotation, loss, revocation, and recovery.
- Prevent downgrade by default.
- Save application state and close operations safely before platform installers run.
- Test interrupted download, corrupt metadata, bad signature, disk exhaustion,
  rollback or recovery, and loss of network.

Signature verification proves update provenance and integrity, not semantic
authority. Every update receives a reviewed machine-readable diff of Tauri
capabilities, custom commands, network destinations, filesystem scopes, native
permissions, and application authority rules. Retain the review with release
evidence, disclose any broadening in release notes, and require explicit consent
before enabling a broader network, privacy, or external-system policy.

### 13. Qualify accessibility

Automated checks include semantic markup, names, roles, states, keyboard behavior,
contrast, zoom, focus, and ARIA snapshots. Manual release checks include:

- Windows Narrator, Magnifier, On-Screen Keyboard, high contrast, and DPI scaling
- macOS VoiceOver and Reduced Motion
- Linux Orca, high contrast, large text, keyboard-only use, and on-screen keyboard

Every primary workflow completes with keyboard and screen reader alone. Focus moves
to blocking error summaries, inline fields retain associated messages, and live
regions announce meaningful stage changes rather than token or progress noise.

Frontend tests use pinned Vitest, Testing Library, and `@vitest/coverage-v8` tooling.
`npm run test:frontend:coverage` enforces the 80 percent line and branch floor through
the general config. `npm run test:frontend:critical-coverage` selects the reviewed
critical module list and enforces 90 percent branch coverage. Generated DTOs,
third-party code, fixtures, and platform bootstrap code are excluded only through a
reviewed checked-in list. Both commands emit retained machine-readable reports and
fail continuous integration below threshold.

### 14. Qualify performance and stability

Initial project targets, to be confirmed on declared baseline hardware before
freeze, are:

- Visible response to input at 100 ms p95
- Frontend event-handler work below 50 ms
- Meaningful cold window by 2.5 seconds p95 and warm window by 1.5 seconds p95
- Idle CPU below 1 percent after stabilization
- Resident UI memory below 250 MB excluding loaded models
- Visible cancelled state by 100 ms while backend cleanup proceeds

Measure start, interaction, navigation, diff, large-document, cancellation, memory,
CPU, GPU, disk, and battery behavior. Long work runs off the UI thread. Performance
regression reports use exact package, WebView, OS, and hardware identities.

### 15. Retain release and screenshot evidence

For every captured state record commit, artifact digest, model digests, OS,
architecture, locale, theme, scale, WebView version, and fixture ID.

Capture from signed passing builds:

- Empty, loading, rewritten, unified diff, unchanged, abstained, cancelled, failed,
  model missing, offline, and update states
- Light, dark, high contrast, 100 percent and 200 percent zoom
- 1024 by 600 and standard desktop sizes
- Platform-specific views where behavior materially differs

Retain accessibility reports, keyboard traces, manual assistive-technology
checklists, performance traces, and reviewed visual diffs beside screenshots.

## Security acceptance

- The exact enabled capability set is machine-audited.
- Every privileged command has positive and negative authorization tests.
- No remote content, untrusted HTML, eval, inline script, or broad plugin authority is
  present.
- WebDriver and backend-mocking plugins, commands, listeners, dependencies, and
  permissions are absent from signed release artifacts.
- External links pass through a narrow Rust allowlist and user confirmation.
- The frontend cannot access files, network, models, profiles, updates, or processes
  outside typed commands.
- Stale events cannot mutate visible or persisted state.
- Update artifacts require signature verification and explicit user action.
- Update qualification retains the reviewed authority diff and verifies any required
  disclosure and consent path.
- A full rewrite completes with all network access blocked after model installation.

## Required test matrix

| Layer | Required evidence |
| --- | --- |
| Rust | Unit, property, integration, fuzz, mutation, authorization, cancellation, and benchmark tests |
| Frontend | Component, reducer, keyboard, accessibility-tree, schema, and mocked-command tests |
| IPC | Schema validation, bounds, acknowledgement barrier, targeted channels, stale events, sequence gaps, snapshot resume, window reload and close, operation ownership, malformed payloads, and fuzzing |
| Instrumented desktop | Test-feature WebdriverIO flows plus dependency, capability, listener, and bundle proof that instrumentation is absent from release |
| Signed platform binary | External black-box install, launch, navigation, rewrite, cancellation, update, recovery, uninstall, dialogs, shortcuts, themes, accessibility, offline behavior, and WebViews |
| Accessibility | Automated plus manual Narrator, VoiceOver, Orca, keyboard, zoom, contrast, and motion checks |
| Visual | Controlled per-platform baselines with human review of every accepted change |

Overall Rust line coverage and frontend line and branch coverage remain at least 80
percent. Rust authorization, IPC adapters, evidence admission, and cancellation
target at least 90 percent line coverage plus decision-table fixtures and mutation
testing. Frontend state reducers and critical IPC presentation target at least 90
percent branch coverage. Every surviving high-risk mutant is dispositioned.

## Exit evidence

The phase closes only when:

- Core workflows pass automated and manual accessibility review.
- Functional and visual behavior passes on WebView2, WKWebView, and WebKitGTK.
- The desktop contains no independent product logic.
- Tauri capabilities, custom commands, CSP, links, and updater pass security review.
- Signed install, upgrade, recovery, rollback where supported, and removal pass on
  declared platforms.
- Performance targets pass or are revised through a recorded evidence-based decision.
- Real screenshots come from passing signed builds and have useful alt text.
- All four refinement passes are complete with no open critical security,
  accessibility, data-loss, packaging, or usability defect.

The handoff to 0.9 includes a stable typed interview state machine, tested desktop
operation model, secure Rust command boundary, packaging pipeline, and accessible UI
that remains complete without microphone or speech models.
